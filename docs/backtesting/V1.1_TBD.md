# backtesting — V1.1 Parking Lot

Follow-ups discovered while writing `V1_PLAN.md` (and consolidated after the Q1–Q10 plan-review decisions) that are deliberately out of scope for v1. Each entry has a short rationale for the deferral and a sketch of what shipping it would entail. Promote an entry to a real `V1.1_PLAN.md` when a coherent slice is big enough to be "a project, not a chore."

Each entry is the parking-lot reference; the in-plan rationale for why it isn't v1 lives in `V1_PLAN.md` § "v1 vs v1.1 scope", § "Architectural decisions", and § "Resolved questions".

## Modeling-realism deferrals

### Margin requirements + borrow costs + locate

v1 has unconstrained short selling (`spec.md` § 4.2 design note). A real shorting model needs:

- Per-asset margin requirement (often regulator-set, e.g., Reg-T's 50%).
- Borrow rate per asset per day (sourced from a borrow-rate feed — new `data_pipelines` domain).
- Locate-availability flag (binary; varies daily; another new feed).
- Margin-call mechanics: when equity / required-margin falls below a threshold, the engine force-liquidates positions to restore the ratio.

Sketch: new `MarginPolicy` component owned by `Backtest`, queried by the broker before each fill. v1.1 entry.

### Partial fills

v1 fills orders completely or not at all. Real markets fill partially based on liquidity. A v1.1 partial-fill model would need:

- A per-asset liquidity profile (e.g., max-shares-per-bar = `0.1 * volume`).
- Fill sequencing across orders contesting limited liquidity.
- A partial-fill audit trail in `info` (one order → multiple fill records).

Sketch: optional `liquidity_fn(asset, bar) → max_fillable_qty` hook on the broker. Default `None` ⇒ v1 behavior. v1.1 entry.

### Limit orders + per-order `execution` override (Q6)

v1 dropped limit orders entirely (`fill_mode` is engine-level, every order fills at the same phase). v1.1 reintroduces:

- A per-order `execution` field on the order dict that overrides the engine's `fill_mode` (`"current_close"` / `"next_open"` / `"limit"`).
- A `limit_price` field, required when `execution == "limit"`.
- Limit fill logic: buy limit at price P fills when bar's low ≤ P; sell limit at price P fills when bar's high ≥ P. Fill at P. Caveat: real intrabar sequencing isn't resolvable on daily bars.
- Limit-order lifecycle: default good-for-day expiry; queue management for unfilled limits at the end of each bar.
- `cancelled_at_terminal` info key for limit orders that were still pending when the timeline exhausted (the original Q6-pre-decision `info` key, now scoped to limit orders specifically).

Sketch: re-introduce the two-phase `process_queue(..., phase)` argument; per-phase dispatch tables keyed on `execution`. v1.1 entry. Pairs naturally with the time-in-force work below.

### Time-in-force semantics (Q6)

v1 has no concept of time-in-force (every order fills in one phase or is rejected). v1.1 adds:

- `time_in_force` field on the order dict: `"day"` (default, equivalent to v1 GFD-for-limits), `"gtc"` (good-til-cancelled), `"gtd:<date>"` (good-til-date), `"ioc"` (immediate-or-cancel), `"fok"` (fill-or-kill).
- Broker `process_queue` consults this when deciding to expire / hold / cancel.

Sketch: requires limit orders (above) to be useful. v1.1 entry, gated on a real caller-side need.

### Slippage model

v1 fills `next_open` orders at exactly the open price. Real fills slip relative to the requested price, especially for large orders.

Sketch: optional `slippage_fn(order, fill_price, bar) → adjusted_fill_price` hook. Default `None` ⇒ v1 behavior. Pairs naturally with the partial-fill model. v1.1 entry.

### Intrabar / multi-resolution data

v1 supports daily bars (and other single-frequency-per-feed setups). The `current_close` execution mode is valid only under the "state is the completed bar" assumption (`goal.md` § "How to apply this"). Intrabar resolution (minute / tick) requires re-evaluating that assumption, possibly retiring `current_close` for intrabar feeds.

Sketch: not trivial. Would require per-feed resolution metadata, re-thinking the master timeline (different feeds at different resolutions), and a new execution-mode taxonomy. Likely v2-scale, not v1.1.

### Cross-calendar alignment

v1 assumes all feeds share the same trading calendar (`spec.md` § 4.1 design note). US equities + EU macro at different holidays would currently leak NaN bars on one calendar that the other treats as open.

Sketch: per-feed calendar metadata + a master-timeline construction that takes the union across calendars + per-asset untradeable masks reflecting each asset's own calendar. v1.1 entry.

### Multi-frequency master timeline + cross-frequency forward-fill (Q3)

v1 is single-frequency-per-engine — every feed shares the trading calendar of the equity feed. The original spec contemplated a multi-frequency master timeline (highest-frequency feed drives the index; slower feeds like quarterly GDP are forward-filled to match), but Q3 deferred this entirely:

- v1 has no macro domain in `data_pipelines` to demonstrate against.
- The two-phase machinery that this would interact with (limit orders, per-order execution overrides) is itself deferred per Q6.
- Resolving multi-frequency before there's a real downstream consumer would over-fit the design.

Sketch: re-introduce `DataHandler._align_and_fill` with highest-frequency-feed detection, per-asset reindex onto the master timeline, and forward-fill (`pandas.DataFrame.ffill()`) for slower feeds. Add `macro` block to the state schema. Add a `test_b3_causal_forward_fill_macro` correctness test using a synthetic quarterly-release substrate. v1.1 entry, gated on the `data_pipelines` macro domain (see "Macro domain in `data_pipelines`" below).

## API / ergonomics deferrals

### YAML-driven config layer

v1 is constructor-args-only (`spec.md` § 6). A `Backtest.from_yaml(path)` would be useful for reproducible-spec backtests checked into version control.

Sketch: a `configs/backtesting/<name>.yaml` schema with `data_feeds_spec` (identifiers + start + end), `engine_args` (initial_cash, lookback, lot_sizes, default_lot_size), and `strategy_spec` (which strategy module to invoke). v1.1 entry; cheap to add.

### Per-feed default lot sizes (OQ-7 in V1_PLAN)

v1 requires per-asset enumeration in `lot_sizes` for any non-default. A per-feed default (`feed_default_lot_sizes={"crypto": 0, "equities": 1}`) would reduce boilerplate for multi-feed portfolios.

Sketch: add a `feed_default_lot_sizes` constructor arg; lookup order = `lot_sizes[asset]` → `feed_default_lot_sizes[feed_of(asset)]` → `default_lot_size`. v1.1 entry.

### Trade-ledger / equity-curve persistence

v1 has no persistence layer (architectural decision IA4 in V1_PLAN). Real workflows want a saved trade ledger + equity curve per run for offline analysis.

Sketch: optional `Backtest.run_to_completion(strategy_fn, output_dir)` helper that drives the step loop, accumulates trades into a `pd.DataFrame`, persists `trades.parquet` + `equity_curve.parquet` + `final_state.json`. Strategy authors that want different shapes still hand-roll. v1.1 entry.

### Typed dataclasses for `state` and `info`

v1 uses dicts (architectural decision IA3 in V1_PLAN). Once the schema stabilizes, promote to `StepState` + `StepInfo` dataclasses for IDE-friendliness and stricter contract enforcement.

Sketch: replace dict assembly in `Backtest.step()` with dataclass construction; provide a `.to_dict()` method for callers that want the legacy shape. v1.1 entry; trivial mechanically, contentious in timing (don't do it before v1 ships and the schema settles).

### Expanded commission-function signature (Q5)

v1 ships the spec'd 3-arg signature `(asset, qty, price) → float`. v1.1 expands to `(order_dict, fill_price) → float` to unblock direction-aware, time-of-day-aware, and maker/taker / tiered commission models. The whole order dict + actual fill price + execution mode are passed in, giving the commission function access to everything needed for realistic models.

Sketch: introduce the new signature behind a sniff (existing 3-arg callables continue to work) or behind a new `commission_fn_v2` arg that takes precedence. Pair with a `commission_models/` module that ships canonical implementations (maker/taker, tiered-by-volume, per-share-with-floor). v1.1 entry.

### `adj_close` price-column knob (Q4)

v1 hard-codes `close` (raw, dividend-and-split-gappy) as the fill-price column. v1.1 adds:

- A per-feed config knob `price_column: dict[feed_name, str] = {"equities": "close"}` selecting either `close` or `adj_close`.
- A one-time documented warning at construction time when `adj_close` is used (every fill in 2010 is at a 2026-adjusted price, distorting share-count math).

Sketch: thread `price_column` through `DataHandler.get_price()` and the broker's fill-price lookup. v1.1 entry. Cheap to add.

### Per-feed `gap_policy` override (Q9)

v1 has a single engine-level `gap_policy` (`"raise"` or `"ffill_zero_volume"`, default the latter). v1.1 promotes this to a per-feed override:

- New constructor arg `gap_policy_per_feed: dict[feed_name, Literal["raise", "ffill_zero_volume"]] | None = None`.
- Lookup order: `gap_policy_per_feed[feed]` → engine-level `gap_policy` default.
- Useful once multi-frequency feeds land (different fill semantics for quarterly macro vs daily equities).

Sketch: trivial dict-lookup wrapper around the v1 logic. v1.1 entry, gated on multi-frequency support landing first.

## Surface / integration deferrals

### Signal adapters (forecaster outputs → actions)

v1 has zero direct dependency on `forecasters`, `analog_mc`, `gbdt`. Strategy authors translate forecaster outputs into action dicts manually. A `backtesting.signal_adapters` module would standardize common translations:

- `analog_mc_quantile_threshold(forecast_result, low_q, high_q) → action` — sell when quantile-Q of next-H-day return < threshold; buy when > threshold.
- `gbdt_probability_threshold(predictions_df, threshold) → action` — buy / sell when calibrated probability crosses threshold.
- `forecasters_path_mean(result) → action` — position-size on expected return.

Sketch: pure-translation functions, no engine dependency. Lives in `src/backtesting/signal_adapters/`. v1.1 entry; gated on a real downstream consumer asking for it.

### `gymnasium.Env` adapter wrapper

The step-loop is naturally Gym-compatible (`spec.md` § 1, goal.md § "What this module is *not*"). A thin `BacktestGymWrapper` would let the engine be used directly as an RL training environment without modifying the engine.

Sketch: subclass `gymnasium.Env`; map `reset()` / `step()` to the engine's; define `observation_space` + `action_space` from the engine's state/action schemas; let the RL agent provide the reward function externally. v1.1 or later; needs a Gym-using consumer to justify the dependency add.

### Streamlit dashboard

Per-module-dashboard convention (`CLAUDE.md` § "Module namespacing"). For backtesting, a useful dashboard view would let the user load a saved trade ledger + equity curve and inspect attribution, drawdowns, per-asset PnL.

Sketch: requires the trade-ledger persistence layer first. v1.1 entry; gated on persistence shipping.

### Multi-broker plugin architecture

v1 has one `ExecutionBroker` (architectural decision IA1 in V1_PLAN). The natural v2 candidate is a `PaperTradingBroker` that submits orders to a real broker's paper API. Extracting a `Broker` protocol then makes sense.

Sketch: extract `BrokerProtocol` from `ExecutionBroker`; `ExecutionBroker` becomes `HistoricalBroker`; new `PaperTradingBroker` implements the same protocol against (e.g.) Alpaca paper API. v2 scope, not v1.1.

## Data-side dependencies

### Macro domain in `data_pipelines` (blocks OQ-3 in V1_PLAN)

v1's master-timeline + forward-fill machinery is designed for the multi-frequency case (`spec.md` § 4.1, D3). But `data_pipelines` v1 ships `us_equities` + `nse_equities` only. A FRED-style `macro` domain (`(date, value)` series per identifier) would unblock multi-frequency real-data demos.

Sketch: not a `backtesting` module change — it's a `data_pipelines` ask. Track in `docs/data_pipelines/V?.?_TBD.md` once we promote it there. The hook is `data_pipelines.fetch("FRED:GDP", start, end) → pd.DataFrame` returning the canonical `(date, value)` schema.

### Borrow-rate / locate feed (blocks the margin work above)

If margin / shorting realism ships, the engine needs a borrow-rate feed and a locate-availability feed. These are also `data_pipelines` asks (new domain), not `backtesting` asks.
