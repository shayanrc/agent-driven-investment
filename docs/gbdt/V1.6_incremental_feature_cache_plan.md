# gbdt V1.6 — incremental feature caching (+ the seed fix)

Direct continuation of `V1.5_feature_build_perf_plan.md`. V1.5 made the feature
build **3.84× faster bit-identically** by vectorizing the hot families. This plan
attacks the *other* axis: the `_019` `/daily-predictions` cadence **rebuilds a
7–10-year feature matrix from scratch every run to emit one new day**, and it
**re-fetches ~1,500 tickers over the network every run** to do it. The build fix
is a *date-extendable* feature cache; the seed is a separate track.

Motivated by the `backtests _019` cadence, but the core change is gbdt
infrastructure — the whole experiment loop benefits (the agent-loop rebuild is
~3 h/cell on sp500 per `feature_cache.py`, and `--resume` currently rebuilds on
any panel growth).

## The empirical profile (2026-07-02 cadence run, this host)

Backfilling **one** new day (2026-07-01) across the 5 tracked cells took **~60 min**
(the skill claims ~30). Measured split:

| stage | detail | wall-time |
|---|---|--:|
| seed | 3 universes over the network — nasdaq 101/101, **russell 1,006/1,006**, sp500 507/507 | **~30 min** (~half) |
| build 1 | sp500 (both champions share) — 486 tk × 7.9 y | 279 s |
| build 2 | **russell1000 #1** — align dropped 44,793 rows | **607 s** |
| build 3 | nasdaq100 — 92 tk × 8.5 y | 42 s |
| build 4 | **russell1000 #2** — align dropped 2,647 rows | **604 s** |
| builds total | russell = 20.2 min (79% of build time) | **~25.5 min** |

Two findings drive the plan:

1. **russell1000 is built twice.** The two candidate cells' `_align_panel`
   (`infer_fresh_predictions.py`) drop *different* gap-fill row-sets (44,793 vs
   2,647) → different index hashes → the in-process `feat_cache` doesn't share →
   two full ~10-min builds of ~880 tickers × 10.3 y, for two **non-deployed**
   cells. (This is the empirical confirmation of "#3" below.)
2. **The build is ~half; the seed is the other half.** Both are russell-dominated,
   and russell cells are `deployed=False`. Incremental caching removes the build
   half; only the seed track removes the seed half.

**Phase-0 discrepancy to resolve:** V1.5 profiled the sp500 build at **76.5 s**
(486 tk × 1,859 d); the cadence measured **279 s** on a near-identical slice —
3.6× slower. Candidates: this host being slower than the V1.5 box, memory
pressure from concurrent multi-universe panel residency (russell's ~2.3M-row
panel is resident in `panel_cache` during the shared build), or a regression.
Re-profile before assuming the incremental design's speedups.

## Goal

Daily cadence **~60 min → ~5 min** without dropping any tracked cell, by:
- making the daily feature build **O(new-days × tickers)** instead of
  **O(7–10 y × tickers)** via a date-extendable cache (**subsumes #2 and #3**), and
- fixing the seed so it isn't a ~30-min network tax (separate track).

Non-negotiable, per `goal.md` + `feature_cache.py`: **the cache is a build-time
optimization that never changes results.** Every emitted feature value must be
**bit-identical** to a from-scratch `build_feature_matrix`. C1 causal / zero
look-ahead is preserved by construction (we never compute a date from later data).

## Why incremental caching subsumes #2 and #3

The two cheaper ideas from the diagnosis:
- **#2 (anchor the slice to `since`, demote the self-check to weekly).** Tried to
  shorten the slice, but the 1,600-td eligibility floor (`data.py:253,310`)
  re-ranks the cross-section under a short warmup → the exact `test.csv`
  reproduction breaks. #2 traded a correctness guard for ~28% off russell.
- **#3 (build one matrix per universe, shared across cells).** A ~1-h win that
  removes the russell double-build.

Incremental caching **avoids the recompute entirely**: freeze the historical
matrix (built once with the *correct* eligible set — the one the model was
trained/tested on) and **only append new dates**. Consequences:
- the cached history still reproduces `test.csv` exactly → **the self-check stays
  valid AND becomes free** (re-predict a few thousand cached rows; no rebuild). No
  slice-shortening, no self-check demotion → **#2 is subsumed**.
- the cache is keyed **per-universe**; every cell of a universe extends the one
  matrix and subsets columns → **#3 is subsumed by construction** (the shared
  build is the cached universe matrix).

Do **#3 as the immediate win now** anyway (it's ~1 h and useful until the cache
lands); the cache then supersedes it.

## The three feature-incrementality classes

Every family in `features.py` falls into one of three classes w.r.t. extending by
a new date. This taxonomy is the design's backbone.

| class | families | value at date *t* depends on | extend by |
|---|---|---|---|
| **A — per-ticker rolling** | F2, F4, F5, F7-roll, F8, F10, F11, F12, F13, F16-native-z | that ticker's last ≤ max-lookback (~200–250 td) rows | keep a **tail** of ~1 y; recompute rows > `cached_max_date`, discard the warm-up overlap |
| **B — per-ticker *stateful streak*** | **F16 `signed_days_outside_band`** (93 cols; ~56% of build per V1.5) | an **unbounded** run-length back to the last band re-entry | a tail is **insufficient** — persist `(run_length, sign)` per (ticker, col, σ) and **seed the extension** |
| **C — cross-sectional per-date** | F14 `*_xs_*`, F7 `dollar_move_xs` | *all eligible tickers'* values **on date *t*** (each date independent) | compute the new date's cross-section from that date's rows + the **current eligible set** |

Class **B** is the crux: `_signed_days_outside_band_one` (`features.py:572`) is a
numpy run-length that can reach back arbitrarily; "keep a 200-row tail" is wrong
for F16. The carried state is tiny (2 numbers per ticker×col×σ) and the extension
is trivially bit-identity-testable (V1.5 already has a 433-case reference for the
streak fn).

## Design — the date-extendable universe cache

A new module `src/gbdt/incremental_feature_cache.py` (sibling to
`feature_cache.py` / `universe_feature_cache.py`), storing per
`(universe, code_signature, eligibility-affecting split fields)`:

- `matrix.parquet` — the full `(date,ticker)` feature matrix up to `cached_max_date`.
- `state/` sidecar:
  - **class-A tail** — the panel tail (≥ max-lookback rows/ticker) needed to warm rolling windows for the new dates.
  - **class-B streak state** — `(run_length, sign)` per (ticker, underlying-col, σ) at `cached_max_date`, preserving the NaN-reset semantics.
  - **class-C eligibility** — per-ticker cumulative row-count + the eligible set, so a new date's cross-section uses exactly the tickers a full rebuild would include.
- `key.json` — reuses `feature_code_signature()` (`feature_cache.py:92`, the
  `source_sha256` of `features.py`) so any feature-code edit forces a cold
  rebuild, plus `cached_max_date`.

**The key change vs today's cache:** `feature_cache.compute_key` folds in
`panel_signature`, which hashes **every** `(date,ticker)` tuple
(`feature_cache.py:143`) → any appended row busts the key → today's cache is
*exact-match* (great for `--resume`, useless for a growing panel). The
incremental cache **must not** key on the panel hash; it keys on
`(universe, code_signature, split-eligibility)` + tracks `cached_max_date`, and
verifies the seam (below) instead of the whole-panel hash.

**Daily extend algorithm:**
1. Load `matrix.parquet` (through `cached_max_date`) + state.
2. Load only the panel **tail** (`cached_max_date − ~1 y … end`) — a tiny load, not 7–10 y.
3. **Seam-integrity check** — recompute features for the last ~K overlap dates from the fresh tail; assert **bit-identical** to the cached values. On mismatch (a provider revision / gap-fill — the `_006`/`_007` bug class), **invalidate + full rebuild**. This replaces "rebuild everything to be safe" and is the incremental analog of the self-check.
4. Extend class-A (recompute tail, keep rows > `cached_max_date`), class-B (seed run-length from carried state), class-C (new dates' cross-sections with the current eligible set; a ticker newly crossing 1,600 rows → rebuild just that one ticker's column from history).
5. Append new rows; persist updated matrix + state atomically (temp-rename, like `feature_cache.write_cache`).
6. Per-cell: subset columns, `self_check` on the (cached) test overlap, predict the new rows, log.

## Correctness gates (non-negotiable — `src/gbdt/`)

Mirror V1.5's discipline; each is a bit-identity proof, not a tolerance:
- **Class-B seam proof.** `full_build == build_to_T ⊕ extend(T→T+k)`, bit-identical, over the V1.5 streak stress set + boundary cases (a run straddling the seam; a NaN at the seam; band re-entry at the seam).
- **Class-C eligibility boundary.** Assert the incremental new-date cross-section equals a full rebuild's for that date, incl. the day a ticker crosses 1,600 rows.
- **Full-matrix parity gate** (extend V1.5's `check_feature_parity.py`): cached-extend vs from-scratch, **all 279 cols bit-identical (max|Δ|=0, NaN-structure identical)** across several append steps.
- **Seam-integrity catches revisions.** A test that mutates a historical cached bar and asserts the seam check invalidates + rebuilds.
- **C1 preserved** — extension is per-ticker chronological / per-date; never reads later data.
- **CI regression tests** in `tests/gbdt/` locking the extend path against a reference, alongside the existing feature-value references.

## The seed track (separate — incremental caching does NOT touch it)

The seed is ~30 min / ~half the run, russell-dominated. Options (not mutually
exclusive):
- **S1 — weekly candidate cadence** (the "#1" idea, now justified by data). Daily
  seeds + scores only the 2 deployed sp500 champions (507 tk); the 3 candidates
  (both russell + nasdaq) refresh on a **weekly** timer. This removes russell
  from the *daily* seed AND build. Cheapest path to the ~5-min daily target.
- **S2 — parallel/batched seed.** `data_pipelines seed` appears serial-per-ticker;
  a batched/threaded fetch could cut the wall-time materially (a `data_pipelines`
  enhancement).
- **S3 — skip-fresh seeding.** Open question to verify first: does the seed
  re-fetch all 1,006 russell tickers each run, or skip already-fresh ones? If it
  re-fetches all, a skip-fresh guard is a large, cheap win.

Recommendation: **S1 daily/weekly split** + **S3 skip-fresh**, with S2 as a
follow-on if the weekly candidate run is still too heavy.

## Phases

- **Phase 0 — re-profile + #3 quick win.** Reconcile the 279 s vs V1.5's 76.5 s
  gap (host / memory pressure / regression). Ship **#3** (share one build per
  `(universe, warmup, alignment)` across cells) as the immediate ~halving of
  russell. Verify the seed's skip-fresh behavior (S3 open question).
- **Phase 1 — extendable universe cache** (class A only): persist matrix + tail,
  extend rolling families, seam check, parity gate. Wire nothing yet.
- **Phase 2 — class B** (F16 streak-state carry) with the seam proof.
- **Phase 3 — class C** (cross-sectional + eligibility boundary) with the
  boundary proof.
- **Phase 4 — wire into the daily runner** (`infer_fresh_predictions.build_scores_multi`
  → try incremental extend, fall back to full build on any seam miss). Cheap
  daily `self_check` on the cached overlap stays as the guard.
- **Phase 5 — seed track** (S1 daily/weekly split + S3 skip-fresh).
- **Phase 6 — validate + document.** End-to-end cadence timing (~5 min target),
  memo, `V1.6_TBD.md` for anything deferred.

## Verification

- `uv run python -m pytest tests/gbdt tests/backtests -q` green, incl. the new
  seam/eligibility bit-identity tests.
- A full daily cadence run produces a forward log **byte-identical** to the
  current from-scratch path for the same `--end` (the `_019` self-check sees
  Δ = 0), at a fraction of the wall-time.
- `--resume` and the agent experiment loop also hit the extendable cache on panel
  growth (the broader win beyond `_019`).

## Key risks

- **A subtle non-bit-identity** in class B/C extension → mitigated by the parity
  gate + seam-integrity fallback (a miss just triggers a correct full rebuild).
- **Provider revisions** silently staling cached history → the seam check is
  exactly this guard.
- **Newly-eligible tickers** (crossing 1,600 rows) needing a per-ticker rebuild →
  a bounded, testable edge case, not the common path.
- **Cache invalidation correctness** — `feature_code_signature` already handles
  feature-code edits; the split-eligibility fields must be in the key too.

## Cross-module touchpoints

Core change is gbdt (`src/gbdt/incremental_feature_cache.py`, `features.py`
helpers, `tests/gbdt/`). Wiring is backtests
(`scripts/backtests/infer_fresh_predictions.py`,
`scripts/backtests/daily_forward_predictions.py`). The seed track touches
`data_pipelines` (seed) + the daily runner (S1 cadence split). Branch:
