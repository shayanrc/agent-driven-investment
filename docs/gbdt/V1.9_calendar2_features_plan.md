# V1.9 — calendar2 feature family (F21) + matched A/B

**Requested by the user.** Add a **month-of-quarter + quarter-of-year** calendar family,
then run a faithful matched A/B through the runner. Mirrors the F17-macro /
F18-F19-fundamentals / F20-VWAP arc (`_262`–`_281`): a new opt-in family, a clean
matched single-fit A/B, and an explicit **one-window / preliminary** verdict — NOT an
automatic promotion.

## Why

A standalone importance check + ablation (done before this branch) found month-of-quarter
and quarter-of-year carry real signal: `moq_sin` ranked **16/297** by gain, and adding the
4 features improved test R-p@K on the representative window. But the effect was
**window-sensitive**, and the standalone fit did NOT reproduce the runner's
calibrated / uniqueness-weighted model. So a **faithful matched A/B through the runner** is
the real test — the standalone importance number is suggestive, not decisive.

F15 already encodes month-of-year cyclically. F21 adds the two positions F15 does not
resolve: *where in the fiscal/reporting quarter* today sits (earnings-season seasonality)
and *which* calendar quarter it is.

## F21 — the feature family (shipped in this branch)

Cyclically encoded to match the F15 idiom (`features.py::calendar_features`), 4 columns:

- `moq = ((month - 1) % 3) + 1` ∈ {1,2,3} → `moq_sin = sin(2π·moq/3)`, `moq_cos = cos(2π·moq/3)`
- `qoy = ((month - 1) // 3) + 1` ∈ {1,2,3,4} → `qoy_sin = sin(2π·qoy/4)`, `qoy_cos = cos(2π·qoy/4)`

`month` is derived from `panel.index.get_level_values("date").month` — trivially causal
(date-only, no look-ahead, same C1 discipline as F15). Asset-agnostic (no per-stock
constants).

**Opt-in tokens** (default `"all"` stays byte-identical — `EXPECTED_TOTAL_COLS == 279`,
locked by a test):

- `all_calendar2` = `_ALL_FAMILIES + ("F21",)` — technical + calendar2 (**no** fundamentals)
- `all_fundamentals_calendar2` = `_ALL_FAMILIES + ("F18", "F21")` — technical + F18 + calendar2

Registered as family id `"F21"`, **NOT** in `_ALL_FAMILIES`. Tests:
`tests/gbdt/test_features_calendar2.py` (columns, moq/qoy oracle, C1 via the leakage
harness, and the `all`=279 / `all_calendar2`=283 token-composition locks).

## The A/B (matched single-fit)

Matched **single-fit** A/B (`max_iterations 1`, default HP, `split.mode: date_aligned`,
`split.train_start: 2019-01-01`, `backend.library: xgboost`, `--snapshot-end 2026-07-06`),
across the representative **nasdaq100 VWAP cells**
`nasdaq100_up_{50pct_25d_dd25pct, 20pct_50d_dd10pct, 40pct_200d_dd20pct}`. For each cell,
two specs identical except `features.candidates`:

| arm | token | reads |
|---|---|---|
| base | `all` | — |
| +cal2 | `all_calendar2` | — |

The arms differ ONLY in `candidates`, so the per-cell delta is clean (the
`[[project-gbdt-macro-features-f17]]` matched-HP rule — never compare via the auto-loop,
which tunes each arm independently and confounds the feature effect with the search).
Compare **test R-Precision@{1,3,5,10,20} + AUC** from each `metrics.json`
(`headline_test.roc_auc`; `segment_diagnostics.test.r_precision_at_k.by_k.<K>`; base_rate
at `...r_precision_at_k.base_rate`).

## Success criteria / verdict

The bar is **two-window robustness**, not a single-window win. F17-macro (`_264`), the
long-horizon F18 (`_278`), F19 (`_279`), and F20-VWAP (`_281`) all looked additive on one
window and failed the second. A calendar2 edge is adopted only if it replicates on an
independent date-aligned window. This branch delivers **one window only** — the memo
explicitly frames it as preliminary and names the second-window replication as the
follow-up. Champion / `/daily-predictions` unchanged regardless. Memo:
`docs/gbdt/_NNN` (next after `_281`).
