# gbdt V1.2 — XGBoost backend + feature-interaction analysis

**Goal**: add a second GBDT backend (**XGBoost**) to the gbdt module so we can analyze how **feature interactions** — pairwise and higher-order — drive the categorical-outcome models, and produce a CatBoost-vs-XGBoost comparison on the same cells. XGBoost is chosen specifically for its interaction tooling: SHAP `pred_interactions` (full per-row interaction-value tensor), `interaction_constraints` (the ability to *forbid* the model from mixing certain feature groups in a single tree path), and a clean split-tree structure for co-occurrence counting.

This promotes the **"Per-experiment library override"** entry in `docs/gbdt/V1.1_TBD.md` (§ lines 75–85) into a real plan + branch, scoped tightly to the *interaction-analysis* use case rather than a generic multi-library framework. It is V1.2 because it is gated behind the V1.1 agent-driven FS+HP loop (Phases 1–2 already merged at `fac7c1a`): the loop's exit-and-resume control flow is backend-agnostic, but three CatBoost-coupling spots remain, and this plan resolves exactly those three.

> **Status: PLAN / SPEC — not implemented.** No code, no `xgboost` dependency, no experiments are added by the PR that lands this doc. The doc is held for the user's in-session review. Implementation follows in a subsequent branch per the phasing in § 9.

## § 1. The capability gap and why now

Today the gbdt module is single-backend. `src/gbdt/model.py::GBDTModel` is a thin CatBoost wrapper; `configs/gbdt/default.yaml::backend.library` exists as a field but only `"catboost"` is accepted (`docs/gbdt/EXPERIMENT_SPEC.md` line 187: *"v1 accepts `"catboost"` only"*). Interaction analysis exists but is **CatBoost-native and coarse**: `scripts/gbdt/diagnose.py::interaction_involvement` / `top_interaction_pairs` (lines 121–136) call `model.get_feature_importance(type="Interaction")`, which is CatBoost's **split-pair co-occurrence** statistic — a single scalar per feature pair, summed over the ensemble. It ranks pairs but gives no per-row signed interaction values, no way to *intervene* (forbid an interaction and measure the calibration cost), and no Shapley-grounded decomposition.

**Why XGBoost specifically:**
- **SHAP `pred_interactions=True`** returns the full `(n_rows, n_features+1, n_features+1)` interaction-value tensor: the signed, additive Shapley decomposition of each prediction into main effects (diagonal) + pairwise interactions (off-diagonal). This is the gold-standard measurement of *"how much does feature A's effect depend on feature B's value, for this specific row?"* — exactly the question goal.md § "What this module is optimizing for" line 33 gestures at (*"handles non-linear interactions"*) but the current tooling can't quantify per-row.
- **`interaction_constraints`** lets us run a controlled experiment: forbid the model from combining feature groups within a tree path, retrain, and measure the calibration/Brier cost. That cost *is* the interaction's contribution to predictability. CatBoost has no clean equivalent.
- XGBoost's `tree_method="exact"` + fixed seed + single-thread is a documented, reproducible determinism recipe (§ 5.1), satisfying the finalization-retrain contract.

**Why now:** V1.1 Phases 1–2 (PR #53, #55) shipped the exit-and-resume loop. That loop is backend-agnostic — it keys only on `(features, hp, val_brier)` and the `DiagnosticBundle` (a backend-neutral dataclass, `src/gbdt/diagnostics.py`). The *only* CatBoost coupling left is in three spots (§ 5). With the loop stable, adding a second backend is now a contained change rather than a moving-target one.

## § 2. Goal, deliverables, and the acceptance test

### 2.1 What "analyze how feature interactions affect the models" concretely means

Three deliverables, in priority order:

1. **Per-cell interaction-strength ranking.** For a fitted XGBoost cell artifact: the top-N feature *pairs* by aggregate SHAP interaction magnitude, plus per-feature **interaction involvement** (total interaction load a feature carries, the XGBoost analog of `diagnose.py::interaction_involvement`). Reported as raw mean-absolute-interaction values + a base reference column (per § "Reporting conventions" — **no lift column**).
2. **Interaction diagnostics in `/gbdt-diagnose` and in the agent-loop request bundle.** `/gbdt-diagnose` already has an "interaction strength" section (SKILL.md § "What it computes" item 5); V1.2 swaps the CatBoost-native co-occurrence for SHAP interaction values when the artifact is an XGBoost model, and feeds a compact summary into the V1.1 `diagnose.json` bundle (D7) so the agent can reason about interaction structure during FS+HP tuning.
3. **CatBoost-vs-XGBoost comparison on the acceptance cell (D6).** Same cell, same split, same uniqueness weights, both backends. Compares: (a) calibration (Brier, Spiegelhalter Z) — *do they tell the same calibration story?*; (b) discrimination (AUC, weighted R-precision — the standard cross-cell metric, per CLAUDE.md); (c) interaction structure — *does SHAP-interaction resolve pairs CatBoost's co-occurrence ranks flat, or vice versa?* Written up as a memo `docs/gbdt/_<id>_catboost_vs_xgboost_h25_interactions.md` + machine-readable headline in `results/gbdt/data/_<id>_data.json`.

### 2.2 Acceptance test (gates the V1.2 implementation PR — a later branch, not this doc)

> **An XGBoost cell runs end-to-end through `/gbdt-experiment` with `backend.library: xgboost`, produces a complete artifact directory (same file manifest as a CatBoost cell), and `/gbdt-diagnose` on that artifact emits SHAP-based interaction values; the loop's finalization-retrain produces bit-identical predictions on a re-run (determinism check), and the CatBoost-vs-XGBoost comparison memo on the D6 cell is written.**

Sub-criteria:
- **A1 — End-to-end run.** `backend.library: xgboost` spec → artifact dir with `spec.yaml`, `model.<ext>` (XGBoost native `.ubj`/`.json`, see § 4.4), `calibration.pkl`, `features.yaml`, `hp.yaml`, `report.md`, `metrics.json`, `iterations.jsonl`, `figs/`, `predictions/`. Same manifest as goal.md § "v1 PR merge gate".
- **A2 — Determinism.** Re-running the same spec + seed reproduces bit-identical `predictions/*.csv` (the finalization-retrain contract, § 5.1). This is a hard pass/fail in CI, not a judgment call.
- **A3 — Interaction output.** `/gbdt-diagnose <xgb_artifact>` emits SHAP interaction values: top-N pairs + per-feature involvement in `diagnose.json` + a heatmap fig.
- **A4 — Agent-loop compatibility.** A `callback_mode: agent_file_protocol` run on an `xgboost` spec pauses/resumes correctly; `loop_protocol.validate_decision` accepts XGBoost HP names and rejects CatBoost ones (and vice versa for a catboost spec). The exit-and-resume checkpoint round-trips.
- **A5 — Comparison memo.** The D6-cell CatBoost-vs-XGBoost memo exists with the three comparison axes (§ 2.1.3) and a verdict the *user* reads (no automated PASS/FAIL — goal.md § "What v1 actually ships").
- **A6 — Replication of completed experiments (CORE implementation-completeness gate; user requirement).** Before *any* feature-interaction experiment, the XGBoost backend must **reproduce the conclusions** of a defined subset of already-completed CatBoost experiments — run the same cell / spec / split / uniqueness-weights on XGBoost and confirm it lands on: (a) the same **calibration story** (Brier in the same ballpark, same Spiegelhalter-Z sign/gate outcome); (b) the same **discrimination** — AUC and **weighted R-precision lift** within tolerance ([[project-r-precision-methodology]]); (c) the **same signal/null verdict** under the compound rule (AUC∈[0.45,0.55] AND R-prec lift <1.2× → null; >1.5× → hidden top-tail signal). Replication is on **findings, not bit-identical numbers** (XGBoost ≠ CatBoost algorithmically) and does NOT require XGBoost to *beat* CatBoost. **Replication set (minimum):** the `_147` nifty50 H=25 cell (the answer key — HP ceiling ~0.164, depth-6 optimal, prevalence-drift ceiling) + **≥1 H=25 cross-market cell** from the memo-#138 corpus (nasdaq100 / sp500 / nifty100). A backend that cannot reproduce these known results is either **mis-implemented** or reveals the finding was **CatBoost-specific** — either way, **STOP and investigate; do NOT proceed to feature-interaction experiments until A6 passes.**

**Sequencing (user directive):** A6 (replicate known results) is the gate; the novel **feature-interaction experiments** (§ 8 Phase 8) come *only after* A6 passes. The acceptance does **not** require XGBoost to *beat* CatBoost on calibration — a miscalibrated XGBoost cell that still *reproduces the established verdict* is *information* (goal.md § "v1 PR merge gate"). The merge gate is: infrastructure-ran-end-to-end (A1–A4) **+ replication of completed experiments (A6)** + interaction output exists (A3) + comparison memo written (A5).

## § 3. Feature-interaction methodology

### 3.1 The three candidate methods

| Method | What it measures | Cost | Per-row? | Signed? | Intervention? |
|---|---|---|---|---|---|
| **SHAP `pred_interactions=True`** (TreeSHAP interaction values) | Shapley decomposition: per-row, per-pair interaction value; main effects on the diagonal. | O(features² · rows) — the dominant cost (§ 3.3). | yes | yes (+/−) | no (measurement) |
| **XGBoost-native split co-occurrence** (`get_score` / tree dump pair counts, the analog of CatBoost `type="Interaction"`) | How often two features co-occur on a root→leaf path, weighted by gain. | O(trees · depth²) — near-free. | no (per-cell aggregate) | no | no |
| **`interaction_constraints`** | The *causal contribution* of an interaction to predictability: forbid feature groups from mixing in a tree path, retrain, measure ΔBrier / ΔR-precision. | One extra fit per constraint experiment. | no | n/a | **yes** |

### 3.2 What to ship (D1 recommendation, expanded)

- **Ship XGBoost-native `pred_interactions` as the headline measurement.** It is the only method that answers the per-row, signed question. Use XGBoost's **built-in** TreeSHAP via `booster.predict(dmatrix, pred_interactions=True)` (≥ v1.3) — the `(n_rows, F+1, F+1)` interaction tensor (diagonal = main effects, off-diagonal = pairwise) — **NOT the external `shap` package**. Per xgblog Part 6, the native path is GPU-capable and runs in *minutes* where the standalone `shap` library takes *days* (≈340× on interaction values; ~1.2M rows/s on 8 GPUs). The `shap` package, if used at all, is for visualization only (R4). Aggregation for the cell-level ranking: **mean absolute interaction value over rows** per pair (a non-negative magnitude), reported alongside a sign-consistency fraction (what fraction of rows the interaction points the same direction — distinguishes a stable interaction from a noisy averaging-to-zero one).
- **Ship native split co-occurrence as a cheap cross-check**, computed from the model's tree dump. It's near-free and gives a second ranking; large disagreement between the two rankings is itself diagnostic (co-occurrence high + SHAP-interaction low ⇒ the pair co-occurs structurally but the interaction cancels per-row). This is also the **fallback when the SHAP-interaction budget is blown** (§ 3.3) on a very large panel.
- **`interaction_constraints` is a Phase-4 *experiment*, not the default measurement.** Use it to validate the SHAP ranking: take the top-K SHAP-interaction pairs, forbid them via `interaction_constraints`, retrain, and confirm the Brier/R-precision degradation tracks the SHAP magnitude. This closes the loop between *measured* interaction strength and *causal* contribution to predictability. It is opt-in (a separate `/gbdt-diagnose --interaction-ablation` mode or a script), never on the hot FS+HP loop.

### 3.3 Cost / feasibility budget for SHAP interaction values

SHAP interaction is the cost driver. The tensor is `(n_rows, F+1, F+1)`; TreeSHAP-interaction is roughly `O(rows · trees · leaves · depth²)`, and the materialized tensor alone is `rows · (F+1)² · 8 bytes`.

Concrete panel sizes (from the existing artifacts + the V1.1 plan's numbers):
- **NSE nifty50 (~48 tickers)**, split 800/400/200/100 = 1,600 rows/ticker ⇒ ~76,800 panel rows; the in-sample matrix for diagnostics is the train+val slice. Feature pool **F = 279** (goal.md § "What this module is not"), but the FS+HP loop typically prunes to ~30–80 active. At F=279, the dense tensor for ~50k rows is `50,000 · 280² · 8 ≈ 31 GB` — **infeasible to materialize densely**. At a pruned F=60, it's `50,000 · 61² · 8 ≈ 1.5 GB` — feasible. At F=30, ~370 MB — comfortable.

**Mitigations (all in the plan; none are "solve it now"):**
1. **Compute interactions on the pruned active feature set, not the full 279-pool.** By the time `/gbdt-diagnose` runs on a *fitted* artifact, the feature set is already the loop's final active set (`features.yaml`). The 279 figure is the iteration-0 pool; the materialized cost is on the active set.
2. **Sub-sample rows for the cell-level ranking.** A few thousand rows is enough to rank pairs stably; the per-row tensor is only needed when the user drills into a specific prediction. Default: cap at `--shap-interaction-rows 5000` (configurable), stratified by segment.
3. **Don't materialize the dense tensor — stream the pair aggregation.** Accumulate mean-abs and sign-consistency per pair in a `(F+1, F+1)` accumulator (small) while iterating row-blocks; never hold the full `(rows, F+1, F+1)` array.
4. **Gate the full tensor behind an explicit flag** (`--interactions full`), default to the streamed aggregate (D7). The agent-loop bundle gets only the top-N summary.
5. **Native co-occurrence is the unconditional fallback** if even the streamed aggregate blows a wall-clock budget on a large US panel (the `/gbdt-diagnose` long-running note already flags ~28 min builds on nasdaq100).

**Determinism split — the interaction compute MAY use GPU even though training may NOT.** The SHAP-interaction computation is a **read-only diagnostic on an already-fit model**, so it can opt into XGBoost's GPU TreeSHAP (the 340× speedup) without touching reproducibility. This is independent of — and must not be conflated with — the **training** determinism contract (§ 5.1), which pins CPU/`exact`/single-thread because the finalization step *retrains* and must reproduce bit-identically. Concretely: `XGBoostModel.interaction_strength(...)` may set `device="cuda"` for the SHAP pass when a GPU is available; `XGBoostModel.fit(...)` may not. Keep the two device choices in separate code paths so a future contributor can't accidentally GPU-accelerate training.

**Reporting (per CLAUDE.md § "Reporting conventions"):** interaction strength is reported as **raw mean-absolute-interaction values** + a per-feature involvement total + the native co-occurrence cross-check; **no lift column** (lift may appear only in narrative prose). The cell-level table mirrors `diagnose.py`'s existing "Top pairwise interactions" table (pair, raw strength), extended with sign-consistency.

## § 4. Backend architecture — the `model.py` seam

### 4.1 The seam (D2 recommendation)

Extract a **thin** protocol; keep `GBDTModel` as the CatBoost impl; add `XGBoostModel`; select via a factory.

```
src/gbdt/model.py            # BaseGBDTModel (protocol/ABC) + make_model() factory
                             # GBDTModel  (CatBoost impl — current code, ~unchanged)
                             # XGBoostModel (new impl)
```

The protocol surface is exactly the 7 members the rest of the codebase calls on a model (verified against `train.py`, `diagnostics.py`, `scripts/gbdt/diagnose.py`):

| Member | Called by | Notes |
|---|---|---|
| `fit(X_tr, y_tr, X_val, y_val, *, early_stopping_rounds, train_weight, val_weight)` | `train.py::_fit_one`, `walk_forward_train` | sample weights = LdP §4.4 uniqueness (§ 5.3) |
| `predict_proba(X) -> np.ndarray` (1-D, P(positive)) | `train.py`, `diagnostics.py` | XGBoost binary `predict` already returns P(positive); no `[:,1]` slice |
| `feature_importance(kind, X_val=, y_val=) -> pd.Series` | `diagnostics.py::build_diagnostic_bundle` | `kind="native"` (gain), `kind="permutation"` (already backend-neutral — pure Brier perturbation) |
| `best_iteration -> int \| None` | `diagnostics.py` | XGBoost `best_iteration` after early stopping |
| `evals_result -> dict \| None` | `diagnostics.py` (learning curve) | XGBoost `evals_result()` has a different nesting; normalize to the `{split_metric: [...]}` shape `diagnostics.py` line 298–304 expects |
| `hp` / `feature_names` / `fitted` properties | several | unchanged |
| `save(path)` / `load(path, ...)` | runner / `/gbdt-diagnose` | format differs (§ 4.4) |

`make_model(backend: str, hp: dict, *, feature_names, random_seed) -> BaseGBDTModel` dispatches on `backend ∈ {"catboost", "xgboost"}`. `train.py` changes from constructing `GBDTModel(hp, ...)` directly (lines 234, 332) to `make_model(backend, hp, ...)`, where `backend` is threaded from the spec (§ 6.2). **CatBoost behavior is byte-for-byte unchanged** — `GBDTModel` keeps its name, its `__init__`, and its validation; `make_model("catboost", ...)` returns it.

### 4.2 New interaction method on the protocol

Add **one** optional protocol method for interactions, since this is the V1.2 raison d'être:

```
interaction_strength(X, *, kind="shap", top_n=15, max_rows=5000) -> InteractionResult
```

- `XGBoostModel`: `kind="shap"` → streamed TreeSHAP-interaction aggregate (§ 3.3); `kind="cooccurrence"` → tree-dump pair counts.
- `GBDTModel` (CatBoost): `kind="cooccurrence"` → wraps the existing `get_feature_importance(type="Interaction")`; `kind="shap"` → CatBoost also supports SHAP interaction (`Pool` + `ShapInteractionValues`), so we can offer the *same* SHAP-based ranking on CatBoost too, which makes the § 2.1.3 comparison apples-to-apples on the interaction axis.

`InteractionResult` is a small JSON-serializable dataclass: `{top_pairs: [(featA, featB, strength, sign_consistency)], per_feature_involvement: {feat: strength}, per_feature_main_effect: {feat: mean_abs_shap}, method: str, n_rows_used: int}`. The `per_feature_main_effect` map (mean |diagonal SHAP|) is carried alongside `per_feature_involvement` (mean |off-diagonal|) specifically so the agent-loop bundle (D7) can apply the *drop-only-if-low-main-AND-low-interaction* rule. This is what `/gbdt-diagnose` and the bundle consume — `diagnose.py`'s current `interaction_involvement` / `top_interaction_pairs` become thin callers of this.

### 4.3 Calibration carry-over

**No change needed — calibration is already backend-neutral.** `src/gbdt/calibration.py` operates purely on `(y_val, p_val_raw)` arrays: `conditional_isotonic`, `isotonic_always`, `spiegelhalter_z`, `apply_calibrator` (lines 32–152) never touch the model object. `apply_calibrator` (line 65) accepts any object with `.predict` (isotonic or Platt). The `train.py::walk_forward_train` calibration block (lines 435–450) consumes `best_model.predict_proba(X_val)` — which the protocol guarantees. So XGBoost's raw probabilities flow through the identical Spiegelhalter-gated isotonic path. The Platt path (`backend.calibration_method: platt`, EXPERIMENT_SPEC line 200, `CalibratedClassifierCV(cv="prefit")`) needs the model to expose an sklearn-compatible surface — flagged as a § 8 open question (XGBoost's sklearn `XGBClassifier` wrapper satisfies it, but our `XGBoostModel` wraps the native `Booster`; if Platt is requested on XGBoost we either route through `XGBClassifier` or fit Platt manually on `(p_raw, y)` — manual is the cleaner, backend-neutral choice and matches how isotonic already works).

### 4.4 Persistence

CatBoost saves `.cbm` (`GBDTModel.save`, line 292). XGBoost saves its native binary `.ubj` (UBJSON, the recommended format) or `.json`. The artifact's model filename becomes backend-determined: `model.cbm` for catboost, `model.ubj` for xgboost. `/gbdt-diagnose`'s loader (`diagnose.py` lines 175–179, currently hard-codes `CatBoostClassifier().load_model("model.cbm")`) must dispatch on the artifact's `spec.yaml::backend.library` (or on the present model file) to load the right backend — a § 6 change. `metrics.json` / `report.md` record the backend so post-hoc readers know which model produced the artifact.

## § 5. The three coupling resolutions

These are the three spots where the V1.1 loop is CatBoost-coupled (the Phase-2 finding). Each must work for both backends.

### 5.1 Coupling #1 — training determinism is load-bearing (finalization retrain)

**The contract:** `train.py::walk_forward_train` selects the best checkpoint across the full val-Brier history (line 415) and, on the exit-and-resume path, **retrains** the best `(features, hp)` config via `_fit_one` (lines 419–426) because the checkpoint stores feature *names* + HP, not the model blob (plan § 0.2 of V1.1). This retrain **assumes bit-identical reproduction** of the original fit. CatBoost guarantees this via `random_seed` + `has_time=True` (ordered boosting is deterministic given the row order + seed) + the fixed `Pool` row order.

**XGBoost resolution — pin a deterministic recipe in `PINNED_HPS_XGB` and hard-fail on override (D5):**
- `tree_method = "exact"` (or `"hist"` *only* with `nthread/n_jobs = 1`; the `hist` histogram build is order-dependent across threads). Default ship: **`tree_method="exact"`, `n_jobs=1`** — slower but bit-reproducible. Documented as the determinism cost of the analysis backend.
- `seed` (XGBoost's seed param) pinned to the run's `random_seed` (42 default).
- `subsample`/`colsample_*` < 1.0 are seeded by `seed`, so sampling is reproducible — *but only single-threaded*. The pin on `n_jobs=1` covers this.
- **No GPU** (`device="cpu"` pinned) — GPU floating-point reductions are non-deterministic.
- Row order is already fixed by `_carve_X_y` → `_gather_segment` (sorted MultiIndex, `train.py` line 119); XGBoost's `DMatrix` preserves input row order, so the same `(features, hp, seed)` + same row order ⇒ identical trees.

**Failure mode if not pinned (the call-out D5 forces):** if `n_jobs>1` with `hist`, or GPU, the finalization retrain produces a *different* model than the in-loop fit. The artifact's `predictions/*.csv` then disagree with the val-Brier the loop selected the checkpoint on — a silent corruption that looks like a calibration mystery, not a bug. So: `XGBoostModel.__init__` runs `_validate_hp_xgb` which **raises** if `tree_method`/`n_jobs`/`device`/`seed` are set to non-deterministic values, mirroring how `model.py::_validate_hp` raises on a `has_time` override (lines 84–90). A1's determinism sub-test (A2) is the CI guard.

### 5.2 Coupling #2 — HP validation is CatBoost-named

**The coupling:** `loop_protocol.validate_decision` (lines 182–295) imports `TUNABLE_HP_RANGES`, `ENUM_HP_VALUES`, `PINNED_HPS` from `model.py` (line 34) and validates the agent's `hp_changes` against them. These are CatBoost HP names (`depth`, `learning_rate`, `l2_leaf_reg`, `bootstrap_type`, …). An XGBoost agent proposing `max_depth`/`eta`/`lambda` would be rejected as "unknown HP" (line 263–266).

**Resolution — backend-conditional sibling tables (D3):**
- `model.py` grows `TUNABLE_HP_RANGES_XGB`, `ENUM_HP_VALUES_XGB`, `PINNED_HPS_XGB` alongside the existing CatBoost tables (which stay as-is, optionally suffixed `_CB` with the unsuffixed names kept as aliases for back-compat).
- A resolver `hp_tables_for(backend) -> (tunable, enum, pinned)` returns the right triple.
- `loop_protocol.validate_decision` gains a `backend` parameter (defaulted to `"catboost"` for back-compat) and uses `hp_tables_for(backend)` instead of the module-level CatBoost imports. The `backend` is threaded from the spec at the one call site (the runner's resume path) — § 6.2.
- `model.py::_validate_hp` likewise becomes `_validate_hp(hp, backend)` dispatching to the right table; `GBDTModel`'s constructor calls it with `"catboost"`, `XGBoostModel`'s with `"xgboost"`.

**Indicative XGBoost tables** (the full set goes in `XGBOOST_HP_REFERENCE.md`, D4; ranges are illustrative, to be finalized in that doc):

```
TUNABLE_HP_RANGES_XGB = {

    "max_depth":         (1, 16),          # ↔ depth
    "min_child_weight":  (0.0, 1_000.0),   # ↔ min_data_in_leaf (loosely)
```

### 5.3 Coupling #3 — `PINNED_HPS` includes `has_time` (CatBoost-only); C6 without it

**The coupling:** `PINNED_HPS["has_time"]=True` (`model.py` line 70) is CatBoost's mechanism for telling its *ordered boosting* to respect the row order as a time order (the C6 walk-forward correctness gate). XGBoost has **no ordered-boosting / `has_time` concept** (V1.1_TBD § "Per-experiment library override" line 83 flags this explicitly).

**Resolution — C6 rests entirely on the split discipline, which is already backend-agnostic:**
- C6 (no look-ahead, walk-forward boundary) is enforced **upstream of the model** by `train.py::carve_single_fold` + `_gather_segment`: each segment is a strictly-forward trailing slice per ticker (`train.py` lines 65–92, 100–127), no shuffling, train precedes val precedes eval precedes test in time. The model never sees a future row in training. This is identical for both backends.
- `has_time=True` in CatBoost is a *second-order* refinement: it makes CatBoost's *internal* ordered-boosting permutation respect time, reducing target leakage *within* the training fold. XGBoost has no such internal permutation — it just fits on the rows it's given, in order. So **XGBoost's C6 guarantee is the split discipline alone**, which is exactly what V1.1_TBD line 83 calls "a weaker correctness guarantee tradeoff."
- **What XGBoost pins instead:** `PINNED_HPS_XGB` (§ 5.2) pins the *determinism* knobs (`tree_method`, `n_jobs`, `device`) — these are XGBoost's load-bearing pins, replacing `has_time`'s role as "the pin you can never override." The plan documents that the C6 guarantee level differs: CatBoost gets split-discipline + ordered-boosting; XGBoost gets split-discipline only. This is **acceptable** because (a) the split discipline is the primary C6 mechanism and (b) the leakage harness (goal.md § "What success looks like" line 58, the Stage-1 synthetic look-ahead test) tests *both* backends end-to-end — if XGBoost's weaker internal guarantee let leakage through, the synthetic-leak test catches it.
- **Acceptance sub-test:** the Stage-1 leakage harness is parametrized over `backend ∈ {catboost, xgboost}`. A planted future-target signal must NOT produce spectacular AUC on either backend. This is the C6 guard for XGBoost.

## § 6. Spec, config, and wiring changes

### 6.1 Spec field

`backend.library: xgboost` is **already a documented field** (`configs/gbdt/default.yaml` line, `EXPERIMENT_SPEC.md` § "backend.library", lines 181–187) — it just currently rejects anything but `catboost`. V1.2 lifts that restriction. No new spec field; the existing one becomes load-bearing. `backend.hp_starting` for an xgboost spec carries XGBoost HP names (validated against `TUNABLE_HP_RANGES_XGB`). The spec snapshot (PR #35) already captures `backend.library`, so post-hoc readers know which backend ran.

### 6.2 Threading `backend` to the three coupling sites

The runner resolves `backend = spec.backend.library` once and threads it:
1. → `make_model(backend, ...)` in `train.py` (replaces direct `GBDTModel(...)` at lines 234, 332). `walk_forward_train` gains a `backend: str = "catboost"` kwarg.
2. → `loop_protocol.validate_decision(decision, spec, known_features, backend=backend)` at the resume call site.
3. → `XGBoostModel._validate_hp_xgb` (internal, via the factory).

Default `"catboost"` everywhere keeps every existing spec + test byte-identical (the same back-compat discipline V1.1 used for `resume_state=None`).

### 6.3 `default.yaml` additions

A `backend.hp_starting_xgboost` block (XGBoost iteration-0 defaults) is added alongside the existing CatBoost `hp_starting`, **OR** (cleaner) `hp_starting` is resolved per-backend: when `library: xgboost`, the runner reads `hp_starting` keys validated against the XGBoost table. Recommend the latter (one `hp_starting` block, backend-validated) to avoid a second near-duplicate block; the indicative XGBoost iteration-0 values (`n_estimators: 1000, eta: 0.05, max_depth: 6, lambda: 3.0, subsample: 0.8, colsample_bytree: 1.0, grow_policy: depthwise, early_stopping_rounds: 75`) live in `XGBOOST_HP_REFERENCE.md`.

### 6.4 `/gbdt-diagnose` dispatch

`diagnose.py` (lines 175–179) loads `model.cbm` via `CatBoostClassifier`. V1.2: load the backend named in `spec.yaml::backend.library`, build the right model object, and route `interaction_involvement`/`top_interaction_pairs` through the protocol's `interaction_strength` (§ 4.2) so the SHAP path is used for XGBoost. The SKILL.md "What it computes" item 5 (interaction strength) gets a note that XGBoost cells use SHAP interaction values, CatBoost cells use co-occurrence (or SHAP if `--shap` is passed).

## § 7. Integration with the V1.1 agent loop

- **The exit-and-resume control flow is untouched.** It keys on `(features, hp, val_brier)` + the `DiagnosticBundle` — all backend-neutral. The checkpoint (`checkpoint.py`) stores feature names + HP dicts + val-Brier history; none of that is CatBoost-specific. The XGBoost HP dict round-trips through the JSON checkpoint identically.
- **Decision validation** now learns the backend (§ 5.2) so an XGBoost agent's `hp_changes` validate against the XGBoost table.
- **Can the agent prune/tune on interaction structure? (D7)** Yes — `diagnose.json` (the V1.1 Phase-3 bundle) gains a compact `interactions` block: `{top_pairs: [...], per_feature_involvement: {...}, method: "shap"|"cooccurrence"}`. The agent gains a third pruning axis beyond importance + correlation: *"feature X has near-zero main-effect importance but high interaction involvement — pruning it would remove conditional structure"* (this is exactly the `constraint_advice` rule-3 logic in `diagnose.py` line 158, but now usable for *pruning* decisions, not just monotone-constraint advice). The full SHAP-interaction tensor stays out of the bundle (size — § 3.3); the bundle carries only the top-N summary.
- **`interaction_constraints` is NOT a loop knob.** Forbidding interactions is a Phase-4 ablation experiment, not a per-iteration FS+HP decision; it stays out of `TUNABLE_HP_RANGES_XGB` and out of the agent's decision schema.

**Test strategy per phase:**

- **Phase 1** — parametrized test: `make_model("catboost", hp_cb)` returns a `GBDTModel` and behaves byte-identically to today (existing `model.py` tests pass unchanged); `make_model("xgboost", hp_xgb)` fits + `predict_proba` returns a 1-D P(positive) in [0,1]; protocol-conformance test asserting both impls expose all 7 members.
- **Phase 2** — `validate_decision` accepts XGBoost HP names under `backend="xgboost"` and rejects them under `backend="catboost"` (and vice versa); out-of-range XGBoost HP raises with the XGBoost-named message; pinned XGBoost HP (`objective`) rejected.
- **Phase 3** — **determinism test (the A2 guard):** fit `XGBoostModel` twice with the same `(features, hp, seed)` + same row order ⇒ bit-identical `predict_proba`; a `tree_method="hist", n_jobs=4` override **raises**. **Leakage test:** planted future-target signal does NOT yield spectacular AUC on the xgboost backend (parametrized harness).
- **Phase 4** — SHAP-interaction aggregator on a small hand-crafted XGBoost fixture: known interaction (e.g. `y = xor(a>0, b>0)`) shows `(a,b)` as the top pair with high sign-consistency; streamed aggregate matches a dense reference on a tiny matrix; co-occurrence cross-check returns a ranking; `interaction_constraints` ablation reduces the measured interaction to ~0 and degrades Brier on the XOR fixture.
- **Phase 5** — end-to-end smoke: an `xgboost` spec runs through `walk_forward_train`; `diagnose.json` carries the `interactions` block; the `/gbdt-diagnose` loader picks the right backend from `spec.yaml`. Resume-checkpoint round-trip with an XGBoost HP dict.
- **Phase 6** — isotonic + Platt applied to a synthetic miscalibrated XGBoost output recovers calibration (Spiegelhalter |Z| drops below threshold); `save`→`load`→`predict_proba` reproduces predictions for XGBoost.
- **Phase 7 (replication gate, A6)** — production validation, not a unit test, and a **hard gate**. Success = the XGBoost run on each replication-set cell reproduces the completed CatBoost cell's calibration story + AUC + weighted R-precision lift + signal/null verdict within tolerance. A documented divergence (e.g. XGBoost flips a verdict) blocks Phase 8 and triggers a root-cause investigation (mis-implementation vs CatBoost-specific finding) — this *is* the core implementation-completeness test.
- **Phase 8 (feature-interaction experiments + memo)** — production acceptance, gated on Phase 7. Success = A1–A5 all met on the D6 cell; the comparison memo reads like a data scientist's lab notebook with the three axes + a user-facing verdict; the `interaction_constraints` ablation confirms the SHAP→causal-contribution link (forbidding top pairs degrades Brier/R-prec in proportion to measured interaction magnitude).

## § 9. Scope boundaries (what's explicitly OUT)

- **Not LightGBM.** V1.1_TBD lists LightGBM + XGBoost; V1.2 ships **XGBoost only** (the interaction tooling is the driver; LightGBM offers no advantage here). LightGBM stays parked.
- **Not a generic multi-library framework.** The seam supports exactly two backends. A registry / plugin system is over-engineering for n=2 (goal.md § "How to apply": don't crystallize a multi-algorithm registry beyond what a real second backend needs).
- **Not a multi-cell sweep.** One acceptance cell (D6). The multi-spec sweep runner is its own V1.1_TBD entry.
- **Not Bayesian/Optuna HP search.** Separate V1.1_TBD entry; the agent loop stays the driver.
- **Not `interaction_constraints` on the FS+HP hot loop.** It's a Phase-4 ablation experiment only (§ 7).
- **Not solving the feature-matrix recompute tax** (§ 10) — flagged, not fixed.
- **No transaction costs / PnL / position sizing** — same anti-rule as the whole module (goal.md § "What this module is not").
- **No new feature families.** The 279-column pool is fixed (goal.md line 85); XGBoost consumes the same asset-agnostic features. Interaction analysis is *over* the existing features, not new ones.
- **Not interaction-guided feature ENGINEERING (parked → V1.3+ TBD).** xgblog Part 6 shows synergistic pairs → *engineered* product/combined features that improve scores. Tempting, but it expands the loop's mandate from selection+HP to *synthesis*, and our feature family is a deliberately fixed asset-agnostic causal set. V1.2 *measures* interactions and uses them to inform *pruning* (D7), not to mint new features. Park synthesis as a future idea; the blog's own caveat (simple products fail when a feature is categorical/signed — e.g. our F16 signed family) is a warning for whoever picks it up.
- **Not wiring gbdt into `forecasters`** — unchanged deferral.

## § 10. Intersecting efficiency caveat (feature-matrix recompute tax)

The V1.1 Phase-2 finding (and the `/gbdt-diagnose` long-running note) is that **every `--resume` launch recomputes the feature matrix** — the checkpoint stores feature *names*, not the materialized `X`. On a large panel this is a per-iteration tax (~5–6 min NSE, ~28 min US). V1.2 makes this caveat *worse* in one spot: the SHAP-interaction computation (§ 3.3) re-touches the in-sample matrix, and `/gbdt-diagnose` already caches `_insample_matrix.parquet` for exactly this reason. **V1.2 does not solve this** — it reuses the existing `_insample_matrix.parquet` cache for the interaction computation (so a repeat `/gbdt-diagnose --interactions full` on the same artifact is fast), and otherwise inherits the recompute tax. The structural fix (DVC-cached feature matrices, **issue #54**) is out of scope and remains parked; this plan only notes that the interaction tooling is a *consumer* of whatever caching #54 eventually delivers.

## § 11. Risks + mitigations

| # | Risk | Mitigation |
|---:|---|---|
| R1 | **Determinism silently breaks finalization retrain** (the most dangerous risk — § 5.1). | Hard-fail pins (D5) + the A2 CI determinism test. Non-deterministic HP combos raise at construction, never at predict-time. |
| R2 | **SHAP-interaction blows the memory/wall-clock budget** on a large panel (§ 3.3). | Compute on pruned active set + row sub-sampling + streamed aggregation + the native-co-occurrence fallback. Full tensor gated behind an explicit flag. |
| R3 | **XGBoost's weaker C6 guarantee** (no ordered boosting) lets in leakage the synthetic test misses. | The Stage-1 leakage harness is parametrized over backend (§ 5.3); split discipline is the primary C6 mechanism and is identical for both backends. |
| R4 | **`shap` dependency weight / version skew** with XGBoost. | **Largely dissolved by the D1 refinement:** interaction values come from XGBoost-native `predict(pred_interactions=True)`, not the `shap` package — so `xgboost` is the only hard new dep. `shap` becomes **optional (visualization only)**, lazily imported; a run that doesn't render SHAP plots never imports it. Pin `xgboost` (and `shap` if the viz path is kept) in the impl branch's lockfile. |
| R5 | **Backend-conditional code paths diverge over time** (catboost path tested, xgboost path bit-rots). | The protocol-conformance test (Phase 1) + parametrizing the existing model/loop tests over backend keeps both paths exercised in CI. |
| R6 | **Comparison memo over-reads a single-cell result** (D6 is n=1). | The memo's verdict is explicitly the *user's* to read (goal.md); the memo states n=1 and frames XGBoost's value as "does it resolve interaction structure CatBoost under-resolves," not "is it a better model." Multi-cell generalization is future work. |
| R7 | **Calibration path assumes sklearn surface for Platt** (§ 4.3). | Fit Platt manually on `(p_raw, y)` (backend-neutral, matches how isotonic already works) rather than routing through `XGBClassifier`. Confirmed in Phase 6. |

## § 12. Open questions (to resolve in-session or during impl)

1. **Brier-as-eval-metric on XGBoost.** CatBoost pins `eval_metric: BrierScore` (`model.py` line 72). XGBoost's built-in `eval_metric` list has `logloss`, `error`, `auc`, `rmse` — no native "BrierScore" (though `rmse` on probabilities = √Brier for binary). Pin `logloss` for early stopping + compute Brier in the diagnostic bundle (which `diagnostics.py` already does, backend-neutrally, lines 245–251)? Or supply a custom Brier eval_metric callable? **Recommend: pin `logloss` for early-stopping; Brier is computed in the bundle regardless.** (D4 finalizes.)
2. **SHAP interaction on CatBoost for the comparison.** CatBoost supports `ShapInteractionValues` — should the § 2.1.3 comparison use SHAP-interaction on *both* backends (apples-to-apples) and reserve native co-occurrence as the per-backend cheap cross-check? **Lean yes** — it makes the interaction-axis comparison method-controlled.
3. **`max_leaves` / `grow_policy` interaction with determinism.** `grow_policy=lossguide` + `max_leaves` is XGBoost's leaf-wise mode; confirm it's deterministic under the single-thread `exact` pin. (Phase 3 determinism test covers this empirically.)
4. **Does the agent need an `interaction_constraints` *suggestion* in the bundle**, or only the measured involvement? Recommend: measurement only in v1.2; constraint-suggestion is a richer agent capability gated on the Phase-4 ablation proving the SHAP→causal-contribution link holds.
