## Patterns

- **Threshold dominates.** The +40% and +50% cells (across all three universes, both horizons) cluster in test AUC 0.66–0.90 with R-p@1 frequently 0.34–0.74 — above the matched-cell weighted base rate. The +10% cells (all three universes, both horizons) sit at AUC ≈ 0.50 with R-p@1 ≈ base rate; no top-tail signal here at any K. The +20% cells fall in between (AUC 0.67–0.70). This is consistent with the prior pattern that rare-positive cells are the ones the model can find, and high-prevalence cells (here, +10% gains over the long horizon have ~40–46% base rate) leave little structural signal for ranking.
- **Horizon effects mixed.** Within the +50% nasdaq strand, H=100 has the higher AUC (0.870) but H=200 the higher R-p@1 (0.603 vs 0.341) — i.e. the longer horizon's top-of-list precision wins despite a lower AUC. The +40% and +50% russell1000 and sp500 strands show a parallel pattern: H=200 R-p@1 ≥ H=100 R-p@1 on the strong-threshold cells. AUC and top-1 R-Precision are tracking different shapes of the prediction distribution.
- **No anti-AUC cells in this sweep.** No cell crosses the V1.3 (AUC ∈ [0.46, 0.54]) ∧ (R-p@10 lift > 1.8×) compound rule — the +10% cells have AUC ≈ 0.50 but R-p@10 ≈ base rate too, so they're null in both signals, not anti-AUC. As expected the V1.3 auto-disables fired on none of these cells (`anti_auc_flag` would be `unknown` since none of these cells had a sweep_row at iter_0 time).
- **n = 19 with no replication.** All read-outs are single-run; treat the threshold/horizon pattern as a fresh-cell prior, not a tested hypothesis.

## Methodology notes

- **V1.4 date-aligned splits worked on long horizons (#229 validated).** Every cell carries `split_mode=date_aligned`, `split_train_start=2019-01-01` (H=100) or `2018-01-01` (H=200), and segments are anchored to NYSE calendar dates that will reproduce across cache growth. The segment_dates contract is satisfied: H=100 cells span train=2019-01-02 → val=2022-03-07 → eval=2023-10-09 → test=2024-07-26 to 2025-05-13; H=200 cells span the matched 2018-01-02 anchor.
- **#226 `--snapshot-end` pin held.** Every cell shows `preflight.snapshot_end_override = 2026-06-04`. Within each (universe, train_start) group the `panel_signature.panel_index_hash` is identical:
  - nasdaq100 + 2019-01-01 anchor: `9c0d7eb38688…` (4 cells)
  - nasdaq100 + 2018-01-01 anchor: `d1bdc7a084fa…` (3 cells)
  - russell1000 + 2019-01-01: `949336de9dd8…` (4 cells)
  - russell1000 + 2018-01-01: `7b0c88f76c7f…` (3 cells)
  - sp500 + 2019-01-01: `0ee999a08e61…` (3 cells)
  - sp500 + 2018-01-01: `120ef6900af9…` (2 cells)

  The hash differs across (universe, anchor) because the row set + date index differ — that's the expected behavior. The #226 contract ("same data → same hash, across cell config changes") holds within each group.
- **#233 follow-up: H=200 anchor leaked off the canonical D2.** H=200 cells could not run with `train_start=2019-01-01` because train_rows + val_rows + eval_rows + test_rows + horizon overflowed the per-ticker window available from 2019; the H=200 specs were pinned to `train_start=2018-01-01`. The V1.4 D2 anchor table currently records 2019-01-01 as canonical; the table needs a second entry for H≥200 (or a horizon-aware anchor rule). Captured for #233.
- **Mid-sweep fix at `28601eb` caught by main sweep.** When the main sweep encountered the first H=200 spec it crashed in `_validate_spec` (`min_rows_per_ticker` was 1600, below the per-ticker window for H=200). The fix landed on `28601eb` and the **same main-sweep process** picked it up for subsequent H=200 cells (it re-imports per cell). The dedicated H=200 waiter therefore only ran the 3 H=200 cells the main sweep crashed on pre-fix (nasdaq100 +10%/+40%/+50% × 200d), and 5 H=200 waiter cells exited code 2 (artifact-exists guard fired — main sweep had already covered them after the fix). Net: 16 main-sweep exit 0 + 3 H=200-waiter exit 0 = **19 successful runs**.
- **`anti_auc_flag = "unknown"` on every cell.** The loop's V1.3 anti-AUC flag reads the canonical CSV at iter_0 time looking for a sweep_row matching the cell name. None of the new `_aligned` names matched (they're fresh entries), so every cell's flag is `unknown` and the V1.3 auto-disables remain enabled. On retrospective inspection the cells don't trip the rule (no AUC ∈ [0.46, 0.54] cell has R-p@10 lift > 1.8×), so the auto-disable behavior was inert here.
- **Canonical CSV regenerate dropped 29 legacy rows.** The regenerate script (`scripts/gbdt/regenerate_r_precision_at_k_csv.py`) walks `predictions/test.csv` across all reachable worktrees and recomputes from scratch. Many pre-#218-rename rows (e.g. `nasdaq100_up_10pct_50d_dd5pct`, `nasdaq100_up_10pct_50d_dd5pct_manual_xgb`, `sp500_up_20pct_25d_dd10pct_manual_cells13`) no longer have a reachable predictions/test.csv — they were either renamed (the `_agentloop`-suffixed equivalents are present + freshly recomputed) or their predictions live on the two corrupted worktrees `wt-exp-midcap150-up50-100d` and `wt-exp-nifty500-up30-50d` that the script's I/O-error-tolerant scanner skipped. This is **pre-existing data hygiene state**, not a side-effect of this branch's changes; the dropped legacy rows are superseded by the `_agentloop`-suffixed variants the script picked up. Net CSV row delta: previous 59 → current 52. The 19 new `_aligned` cells are all present.
- **All 19 rows have the 8 calendar-date columns populated.** Spot-checked: every `_aligned` row has 18 fields (10 metric + 8 date) with train_start, train_end, val_start, val_end, eval_start, eval_end, test_start, test_end all non-empty.
