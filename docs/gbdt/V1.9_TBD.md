2. **Content-blind cache keys → stale results after a data correction** *(soundness
   bug; cross-module — see also `docs/forecasters/V2_TBD.md` #18).* gbdt caches key on
   the `(date, ticker)` index / code+config hash but NOT on OHLCV **values**, so a
   values-only data correction (e.g. the V5 split-adjustment re-seed) is invisible to the
   key and stale features are served. Two gbdt instances:
   - `panel_signature` (`src/gbdt/data.py`) hashes only the index → won't detect a
     values-only correction. Every downstream feature cache inherits the blind spot.
   - the on-disk **incremental feature cache** (`data/gbdt_incremental_cache`, 19G):
     keyed on `cache_key(universe, warmup_start, min_rows, align_signature)` — after the
     V5 fix it held stale **unadjusted** features; only the `extend_matrix` **seam check**
     (a lucky secondary guard) caught the mismatch, forcing a full rebuild every infer
     (the V5 plan documents this; the cache was cleared operationally, commit `af4f7e4e`).
     A spuriously-passing seam check would serve unadjusted features to `/daily-predictions`.

   **Fix (shared with forecasters #18):** fold a **data-content signature** into each
   cache key — a cheap hash/checksum of a sample of the OHLCV **values** (or the
   re-seed / provider version stamp), so a values-only correction auto-invalidates.
   Regression test per cache: correct one bar → assert cache miss (not a stale hit).
   **This bit for real in V5** — promote from parked to a real fix, not "nice to have."

3. **Cold-build speedup via F16 streak-seed** (the real payoff behind the `--fast-path`
   foundation, commit `15ac9ff9`). The infer cold build is ~28 min/sp500-cell because it
   builds the full ~7y feature matrix. The `--fast-path` foundation shrinks eligibility to
   a cheap COUNT and the panel to a short window, but **F16 caps the win**: `signed_days_
   outside_band` is an unbounded streak (105 of the champions' 279 features) whose faithful
   value needs history back to the last band-crossing (observed max ~975 td). So the panel
   can't drop below ~6y without corrupting F16 in the **forward** window — which the
   `self_check` does NOT guard (it only reproduces the *test* window).
   **The fix:** cold-seed F16. Compute the 31 F16 meta-underlyings (F7 + F14-xs + F16-native
   z-scores) over deep history, run `_signed_days_outside_band_one` to get the streak STATE
   at `panel_start−1`, then hand it to the existing `_continue_streaks` /
   `extend_matrix_full` continuation (which already carries streaks from a *warm* cache —
   this makes a *cold* seed). Bounded families (F1–F15 + F16-native) then need only a ~500-td
   tail. Estimated ~2× on cold builds (build 279 feats × short window + 31 underlyings ×
   deep window, vs 279 × full). **Caveats that make this its own branch, not a session
   patch:** (a) the F14 cross-sectional underlyings still need deep-history compute for the
   seed (not free); (b) getting F16 wrong is silent — a **forward-window** faithfulness
   check (score a date range with vs without the seed, assert match) is mandatory, since the
   `self_check` can't see it; (c) value is narrow — only the *first* cold build per cell
   (the warm incremental cache already handles repeats). Function map is in the branch notes.
   **Cross-cell sharing is NOT a route** — the two champions have identical rosters but
   different `align_signature` (horizon-dependent label availability near segment ends → the
   50d vs 25d cells drop different training rows), so they legitimately need separate builds.

## 4. date_aligned R-Precision@K skipped when `test_rows <= horizon_days` (labels present)

**Symptom.** A date_aligned run with `split.test_rows <= target.horizon_days` (e.g. sp500 +50%/50d with `test_rows: 50`) emits `[test_split] Test segment expected to be EMPTY: horizon_days=50 >= split.test_rows=50 ...`, then finalizes with `metrics.json::headline_{eval,test}.r_precision_at_k == None` and empty R-Precision@K tables in `report.md` — **even though the labels are fully present**. Observed in `sp500_up_50pct_50d_dd25pct_adjfinetune`: `predictions/test.csv` had 24,300 rows with `y_true` 100% non-null, and headline Brier/AUC were computed (test AUC 0.9028), yet R-p@K was skipped for BOTH eval and test.

**Root cause.** The "test expected empty" guard assumes the test segment sits at the data edge (snapshot == test_end), so the trailing `horizon` rows would be unlabelable. But when `--snapshot-end` is far past `test_end` (here snapshot 2026-07-06 vs test_end 2026-03-12, last labelable ~2026-04-24), the forward windows ARE complete and labels get computed — the guard mis-fires and the downstream R-p@K computation is skipped anyway.

**Impact.** R-Precision@K — the canonical cross-cell headline — is silently dropped for period-matched date_aligned cells whose `test_rows <= horizon`, and the registry row is not written. Workaround: compute R-p@K directly from `predictions/{eval,test}.csv` (per-day top-K by `p_calibrated`, macro-avg over days `R_q>0`). The guard should test `snapshot_end - test_end >= horizon_days` (labels available) before declaring the test empty / skipping R-p@K, not `test_rows >= horizon_days`. **NB for the canonical-periods retrains:** the explicit-boundary `test` window is a full year (~250 td) so `horizon < test_rows` for all cells ≤ 200d and the guard should NOT fire — but verify `metrics.json::headline_test.r_precision_at_k` is populated on each retrain; if null, apply the workaround.
