## 1. Motivation

### 1.1 What V1.3 Option A solved — and what it didn't

V1.3 Option A (the eval-R-p@K + anti-AUC-flag bundle, PR #112/#220) closed the **observability** gap on anti-AUC + strong-top-1 cells: the agent now reads `eval_r_precision_at_k`, sees the `anti_auc_flag`, gets a `degenerate_sink_warning`, and the runner auto-disables the L1 tie-break + val_brier auto-plateau on flagged cells. Cell-5 A4 validation hit R-p@1=0.7143 (above the 0.6714 sweep-baseline PASS floor; below the manual track's 0.8286 ceiling) via the in-loop calibrated oracle path in PR #115.

**The gap that remains is cold-start.** Iter_0 still launches from the default HP envelope. For CatBoost that's depth=6 + lr=0.05 + ~1000 iters; for XGBoost it's depth=6 + eta=0.3 + no early-stopping + n_estimators=100. On anti-AUC cells like cell-5 — where the winner is a **6-tree, max_depth=2 XGBoost (≤24 leaves, val_brier RIGHT at baseline)** — the default starting envelope is structurally wrong. Even with Option A's observability, the loop's per-iter HP step (`hp_changes`) walks one knob at a time from a wrong starting point; the tiny-model regime is many synchronous-knob steps away and the loop's `max_iterations: 16` cap may not be enough to reach it.

### 1.2 The cell-5 cliff (quantified)

| Track | Test R-p@1 | vs sweep | Mechanism |
|---|---:|---:|---|
| Sweep (CatBoost defaults, untuned) | 0.6714 | (baseline) | CatBoost defaults sit in a structurally-OK regime for this cell |
| Agent loop pre-V1.3 (mcw=10, γ=1) | 0.5429 | **−19%** | Heavy reg pushed toward the degenerate sink |
| V1.3 Option A loop (`_223` revalidation) | 0.7143 | +6.4% | In-loop calibrated oracle saves the run; still below sweep+24% manual ceiling |
| **Manual track ([_211](_211_cell5_manual_tuning_xgb.md))** | **0.8286** | **+24%** | 6-tree depth-2 XGBoost, eta=0.1 + ES=30, FS=top-130 |

The manual workflow had a **scout phase** (stage 2 of the 5-stage methodology — single-knob response curves across 8 knobs, ~35 fits, mapping val_brier × eval R-p@K before committing to a mix-and-match). The cell-5 winner emerged from THAT scout: the response curves showed `depth=2/3` was the inverted-U minimum, `eta=0.1+ES` was the sweet spot, and `gamma/alpha` curves descended to the degenerate sink (so they were ruled out). Without the scout, the manual track would have iterated from the wrong defaults too.

### 1.3 The N=3 evidence — be humble about what scouting solves

The cell-5 manual methodology was applied to cells 1+3 in [_225](_225_cells13_methodology_replication.md). It **FAILED on both** — cell-1 manual peaked at 0.6600 vs sweep 0.800 (−14 pts); cell-3 at 0.4267 vs sweep 0.600 (−17 pts). The dominant gap on cells 1+3 was **XGBoost-vs-CatBoost backend choice**, not anything FS/HP could close. The 5-stage methodology only works when the loop's val_brier objective is misaligned (rule 10 precondition — `anti_auc_flag == "true"`); on strong-AUC cells like cells 1+3, the methodology cannot even MATCH the un-tuned sweep baseline.

**Implication for Option B's acceptance criteria**: the scout phase must NOT be evaluated against "matches manual baselines on strong-AUC cells 1+3" — because the manual baselines themselves don't beat sweep on those cells. The scout's value lives in cells where rule 10's precondition holds (anti-AUC + strong-top-1). Acceptance bands need to reflect this: cell-5 is the strong gate; cells 1+3 are regression gates (Option B must NOT regress them, but neither must it match an unreachable target).

### 1.4 What Option B operationalizes

Stage 2 of the manual 5-stage methodology — **single-knob response curves before iter_0** — codified into the runner. Concretely: between Phase 1 (data build) and Phase 2 (iter_0) of `/gbdt-experiment`'s lifecycle, run a small coarse grid sweep across 4 knobs (likely `depth × eta × colsample_bytree × min_child_weight`), score each config on val_brier + eval R-p@K (the Option A oracle), pick the winner, and seed iter_0's `hp_starting` from it. The inner FS+HP loop (Phase 3) runs as before, but starting from a cell-tuned envelope instead of a fixed default.

## 2. Goals + non-goals

### 2.1 Goals

- **G1**: Eliminate the "wrong starting depth" pathology on cells where the manual scout would have found a structurally-different regime. Concrete target: cell-5 R-p@1 ≥ 0.75 (above V1.3 Option A's 0.7143; within 10% of the manual 0.8286 ceiling).
- **G2**: Match or beat the V1.3 Option A loop's outcome on cells where rule 10's precondition holds (`anti_auc_flag == "true"`). NOT cells where scout has nothing to add (rule 10 doesn't apply; loop already converges from defaults).
- **G3**: Don't regress cells where the loop already does well — specifically cells with `anti_auc_flag == "false"` (rare-event cells, strong-AUC cells) where defaults are already in a structurally-good regime per N=3 evidence in [_225](_225_cells13_methodology_replication.md).
- **G4**: Keep the inner-loop iteration budget bounded — scout runtime ≤ 2× the cost of a single iter_0 train, total `/gbdt-experiment` wall-clock cap-bounded by `scout_runtime + max_iterations × iter_train_cost`. No unbounded scout.
- **G5**: Surface scout outputs in `metrics.json` for cross-cell comparison (response surface shape becomes data).

### 2.2 Non-goals

- **NG1**: Don't replace the inner FS+HP loop. Option B is a Phase 1.5 addition before iter_0 — Phase 2 + Phase 3 + Phase 4 (calibration) + Phase 5 (artifacts) are unchanged.
- **NG2**: Don't add a backend. Still CatBoost + XGBoost only. Scout uses the spec's declared backend.
- **NG3**: Don't change V1.3 Option A's observability. `eval_r_precision_at_k`, `anti_auc_flag`, `degenerate_sink_warning`, `weighted_base_rate_brier`, `eval_segment_size` stay as-is in the iter bundle. Scout adds new fields IN ADDITION TO these.
- **NG4**: Don't ship an adaptive scout (Bayesian, multi-armed-bandit, sequential model-based). The scout is a one-shot coarse grid; adaptivity is V1.5 territory (parked in §9).
- **NG5**: Don't ship per-fold scout. Walk-forward currently runs 1 fold (`Fold.train_idx + val_idx + eval_idx + test_idx`); the scout runs on that one fold. Multi-fold scout is V1.5.
- **NG6**: Don't auto-tune the scout grid. The grid is spec/preset-driven; scout-grid optimization is out of scope.

## 3. Scope

The scout phase fits between Phase 1 (data build) and Phase 2 (iter_0) in `/gbdt-experiment`'s lifecycle. Concretely:

```
Phase 0 — Infrastructure preflight (V1.4 cache-currency + WAL + disk)
Phase 1 — Data build (universe, features, target, segment carve)
Phase 1.5 — SCOUT (NEW; V1.3 Option B) — coarse grid sweep, pick winner, set iter_0 starting envelope
Phase 2 — Iteration 0 (now starts from scout winner's HPs instead of defaults)
Phase 3 — FS+HP loop (iter 1 .. max_iterations) — unchanged
Phase 4 — Calibration — unchanged
Phase 5 — Artifact emission — unchanged
```

### 3.1 Scout mechanics (sketch — exact spec is in D1–D10)

For each config in the scout grid:
1. Fit the backend (one fit; no FS pruning; full feature pool).
2. Score val_brier + eval R-Precision@K (canonical formula).
3. Record the config row in `scout_results.jsonl`.

Pick the winner config by the scout oracle (D2 — `eval_R_p_at_1`? `eval_R_p_at_K` for what K?). The winner's HP dict becomes iter_0's `hp_starting`.

### 3.2 What the scout does NOT do

- It does NOT run FS. The scout's feature pool is the full candidate set; FS happens in the loop after scout.
- It does NOT iterate. Each config is one fit, one score, done.
- It does NOT pick the final model. The scout's winner is iter_0's starting envelope; the loop still does FS+HP refinement on top.
- It does NOT bypass V1.3 Option A. The anti-AUC flag + eval R-p@K + degenerate-sink warning still flow through every iter bundle.

## 4. Open decisions (D1–D10)

These are intentionally LEFT OPEN. The main session walks through them with the user, locks each, then a follow-up branch implements.

### D1 — Knob grid: what dimensions, what values?

**Cell-5 manual evidence** (`_211` stage 2): 8 single-knob curves were swept (gamma, alpha, max_depth, n_estimators, scale_pos_weight, colsample_bytree, max_bin, subsample). 4 had non-degenerate sweet spots; 4 (gamma, alpha, n_estimators, subsample) were either degenerate or noise.

**Cell-1+3 manual evidence** (`_225`): the eval ordering of single-knob sweeps was unreliable as an oracle (cell-3 eval R-p@1 leader was second-WORST on test). The scout-as-data-source is fine; the scout-as-oracle is suspect on cells where eval-test correlation is weak.

| Option | Grid | Pros | Cons |
|---|---|---|---|
| **D1.A** | `max_depth × eta × colsample_bytree × min_child_weight` — 3×3×3×3 = 81 configs | Comprehensive; covers all 4 non-degenerate cell-5 knobs | 81 fits × ~5s each = ~7 min on hist+nj=8 (cached features); CatBoost variant per-fit cost is 30–120s → 40 min–2.5 hr — concerning |
| **D1.B** | `max_depth × eta × colsample_bytree` — 3×3×3 = 27 configs | 1/3 the configs; still covers the cell-5 winner's region | Drops `min_child_weight` axis (the L2 grid winner per playbook rule 7 — material on rare-event cells) |
| **D1.C** | `max_depth × eta` — 3×3 = 9 configs | Tiniest scout; quickly maps depth×lr response | Misses colsample (the +16% jump on cell-4) and mcw (rule 7 material) |
| **D1.D** | Sequential scout: D1.C first (9 fits), then conditional-extend if winner is on the grid edge | Adaptive; balances cost vs coverage | More machinery; "conditional-extend" logic adds complexity |

Sub-question: should the grid values be **backend-specific**? Cell-5 winner is XGBoost-shaped; CatBoost would use different value ranges. Two sub-options:
- **D1.x.i**: One universal grid spec, validated against backend bounds, but values are backend-agnostic (e.g. `max_depth ∈ {2, 3, 6}`).
- **D1.x.ii**: Spec carries `scout_grid_xgb` + `scout_grid_catboost` keys, runner picks based on `backend.library`.

### D2 — Scout oracle: which metric picks the winner?

| Option | Oracle | Pros | Cons |
|---|---|---|---|
| **D2.A** | `eval_R_p_at_1` (matches cell-5 K=1 specialization) | Aligned with the operating metric for top-pick portfolios; explicit per playbook rule 10 | Q_days × 1 pick/day = small sample → noisy (cell-3 stage-5 eval R-p@1 was actively misleading per _225) |
| **D2.B** | `eval_R_p_at_K` for K=10 (matches sweep's "lift" framing) | More samples per config → less noise; aligns with sweep CSV's R-Precision@10 column used by the anti-AUC flag | Doesn't optimize for top-1 specifically — cell-5's K=1 win wouldn't be picked by this |
| **D2.C** | Composite: `(eval_R_p_at_1 + eval_R_p_at_5) / 2` | Balances top-1 specialization vs noise reduction | Ad-hoc weighting; could mask real K=1 winners |
| **D2.D** | val_brier (existing loop oracle) | Cheap; no eval predict needed during scout | Provably wrong on anti-AUC cells per rule 10 + _211 F1 |
| **D2.E** | Conditional: when iter_0-equivalent diagnostics flag `anti_auc_flag == "true"` use eval R-p@K (D2.A or D2.B); else val_brier | Adapts to cell shape | Requires running an iter_0-equivalent BEFORE the scout (chicken-and-egg) OR running scout twice with different oracles |
| **D2.F** | Both: rank configs by val_brier AND eval R-p@K, ship a tie-break rule (eval R-p@K wins on anti-AUC cells; val_brier wins elsewhere) | Honest about the trade-off | Same chicken-and-egg as D2.E for the anti-AUC flag |

Sub-question: should D2's "winner" be a SINGLE config, or a SHORTLIST? Top-3 by oracle, then a second narrow-grid pass on each, then commit? Top-N adds a phase.

### D3 — Scout runtime budget

| Option | Cap | Pros | Cons |
|---|---|---|---|
| **D3.A** | Hard wall-clock cap: `scout_wall_clock ≤ 5 min` for XGBoost, `≤ 30 min` for CatBoost. Configs that don't fit get dropped (in submission order). | Predictable wall-clock; bounded resource use | XGBoost fit times can spike (deep tree + many features); cap may drop configs heterogeneously |
| **D3.B** | Hard N-config cap: `scout_n_configs ≤ 27` regardless of backend. | Reproducible config-count; pairs well with D1.B | Doesn't bound wall-clock; CatBoost 27-config scout = ~30–60 min |
| **D3.C** | Both: `min(wall_clock, n_configs)`. Run configs in order; stop when either cap hits. | Best of both | Most knobs; configs run in declared order matters |
| **D3.D** | No cap — let it run to completion. | Simplest | Risk of unbounded CatBoost scout on slow cells |

Sub-question: should the scout fit be **time-limited per-config** too (e.g. `fit_timeout_per_config`)? Cell-5's 6-tree winner fits in 3s; a degenerate 1000-tree config on the same cell could take 60s. Per-config timeout would standardize.

### D4 — Scout integration with the existing modes: `default` vs `agent_file_protocol` vs `sweep_mode`

| Option | Applies to | Pros | Cons |
|---|---|---|---|
| **D4.A** | All 3 modes (default, agent_file_protocol, sweep_mode) get the scout when enabled. | Consistent; one code path | Sweep mode already runs untuned CatBoost defaults — scout would increase per-cell cost across the sweep |
| **D4.B** | Only `agent_file_protocol` gets the scout (the agent-driven, per-cell tuned path). `default` + `sweep_mode` stay untouched. | Sweep mode keeps its "no tuning" semantics; agent mode gets the cold-start lift | Default mode + smoke tests run with old behavior; scout has no smoke-test path |
| **D4.C** | `agent_file_protocol` + `default` only; `sweep_mode` opts in via explicit `sweep.scout.enabled: true`. | Default gets coverage for smoke tests; sweep stays cheap unless opted in | Three-way split is more spec surface area |
| **D4.D** | Only `default` mode (scout produces a fixed starting envelope; loop applies the fixed callback from there). | Simplest; ablation-friendly | Agent mode (production surface) doesn't benefit |

Sub-question: should the scout itself be agent-driven (parallel `agent_file_protocol` cycle) or batch (runner-driven)? Cell-5's manual scout was effectively script-driven (`/tmp/cell5_response_curves.py`); the agent didn't iterate, just submitted the grid. Batch is simpler.

### D5 — Scout output → iter_0 — what does the scout actually CHANGE?

| Option | What scout sets on iter_0 | Pros | Cons |
|---|---|---|---|
| **D5.A** | Only `hp_starting` (HP dict). Feature pool starts at the full candidate set (FS still happens in the loop). | Minimal coupling; scout is HP-only | Doesn't capture cell-5's "FS to top-130 + light reg" combined win — FS+HP are intertwined |
| **D5.B** | `hp_starting` + feature pool subset (e.g. drop importance < cliff-cut threshold from scout-winner's importance map). | Captures the "FS+HP combined" intuition | Couples scout to FS — but scout doesn't iterate FS; "cliff-cut from one config" may be misleading |
| **D5.C** | `hp_starting` + `feature_weights` (down-weight low-importance features but don't drop). | Soft FS; loop can recover dropped features | More machinery; feature_weights is a CatBoost-only param |
| **D5.D** | `hp_starting` + sticky knobs (the scout winner's HPs become `hp_pinned` for the first N iters, not just `hp_starting`). | Prevents the loop from immediately walking away from the scout winner | Reduces agent agency; agent may have reason to deviate from scout |

Sub-question: should the scout report a "confidence" signal (e.g. "winner's eval R-p@1 is 0.7 vs second-place 0.69 — close margin → scout is uncertain")? If yes, low-confidence scout → use defaults instead.

### D6 — Cache behavior: scout-time feature matrix sharing

Background: the universe feature matrix is cached at `panel_signature` keys (`#226` cache-key stability fix; cell sharing across siblings). Scout-time:

| Option | Behavior | Pros | Cons |
|---|---|---|---|
| **D6.A** | All scout configs reuse the same feature matrix (one build, N fits). | Optimal — feature build dominates total cost | Already the natural behavior; no special machinery |
| **D6.B** | Per-config feature subset (e.g. test FS aggression as a knob). | Lets scout vary FS too | Defeats cache; bloats wall-clock |
| **D6.C** | Per-backend feature matrix (CatBoost native categoricals; XGBoost numeric-only). | Backend correctness | Need 2 cache slots per universe; doubles cache size |

D6.A is almost certainly the answer; this exists to flag the sub-question of "do we PIN the feature matrix at scout time and forbid downstream features.py changes during the scout?" The honest answer is yes, but it's worth surfacing.

### D7 — Scout reporting: what lands in `metrics.json`?

| Option | What scout emits | Pros | Cons |
|---|---|---|---|
| **D7.A** | `metrics.json::scout` block with: `(grid_spec, n_configs, configs[i].hp, configs[i].val_brier, configs[i].eval_R_p_at_K, winner_idx, runtime_seconds)`. | Full response-surface data; supports cross-cell mining | ~5–20 KB depending on grid size; negligible |
| **D7.B** | A separate `scout/` subdirectory with `scout_results.jsonl` + a `scout_winner.json` summary; `metrics.json::scout` carries only the winner. | Cleaner top-level metrics.json | Two files to load for analysis |
| **D7.C** | Both — full scout dump in `scout/scout_results.jsonl` AND winner summary in `metrics.json::scout`. | Best of both | More files |
| **D7.D** | Render scout response curves as figures (`figs/scout_response_curves.png`) — one PDP-like panel per knob, color-coded by val_brier and eval R-p@K. | Visual feedback; great for memos | Adds matplotlib calls in the scout path |

### D8 — Scout-disable conditions: when to SKIP the scout

Not every cell benefits. Per [_225](_225_cells13_methodology_replication.md), on strong-AUC cells (cells 1+3) the manual methodology FAILED — scout has nothing to add when defaults are already in a structurally-good regime.

| Option | Skip-scout condition | Pros | Cons |
|---|---|---|---|
| **D8.A** | Always run scout unless explicitly disabled (`backend.scout.enabled: false`). | Simple; agent always gets the data | Wastes wall-clock on cells where scout doesn't help |
| **D8.B** | Auto-skip on `anti_auc_flag == "false"`. Need iter_0-equivalent run before scout to compute the flag — chicken-and-egg (or use sweep-CSV-lookup at scout-time). | Targets scout to its intended use case | Cells where the flag is `"unknown"` (no sweep row yet) get scout by default |
| **D8.C** | Auto-skip when scout-time iter_0 train Brier < threshold (cell already "easy" by some heuristic). | Empirical | Threshold is hard to pick; "easy" is cell-shape-specific |
| **D8.D** | Always run scout — but if scout winner's eval R-p@K is below baseline (defaults' eval R-p@K), discard scout result and use defaults. | Self-validating; honest about "scout had nothing to add" | Adds a "scout-baseline-comparator" mini-iter that's almost as expensive as a full scout config |

Sub-question: should the iter_0-equivalent baseline run BEFORE the scout always, to give the scout a "vs defaults" comparator? This is a "scout zeroth config = defaults" answer.

### D9 — Scout failure handling: what if scout's best config is below baseline?

Three cases:
1. Scout winner's `eval R-p@K` < `defaults' eval R-p@K` → scout couldn't beat the cold start.
2. Scout winner's `val_brier` ≈ degenerate sink (the cell-5 anti-AUC pathology, fired in scout instead of in the loop).
3. Scout runtime cap (D3) hit before completion → only partial response surface available.

| Option | Behavior | Pros | Cons |
|---|---|---|---|
| **D9.A** | Discard scout, use defaults for iter_0; log the failure. | Simplest; "scout is advisory" | Wastes scout's wall-clock; downstream agent has no scout signal |
| **D9.B** | Use scout winner regardless; log a warning. Let the loop iterate from scout-winner. | Scout always has effect | Cell-5 anti-AUC pathology could fire in scout → iter_0 starts from sink → loop has to dig out |
| **D9.C** | Scout outputs are an advisory shortlist; the agent reads the scout block in iter_0's bundle and decides whether to apply (`hp_starting` is fetched from the file at agent-side, not auto-applied). | Maximum agent agency | Half-measure; auto-apply is the value proposition |
| **D9.D** | Use scout winner UNLESS `degenerate_sink_warning` is triggered in scout — in which case discard scout, fall back to defaults, AND flag the cell as "scout-degenerate" in metrics.json. | Targets the cell-5 failure mode | The defaults may not be better; this just side-steps the question |

### D10 — Cross-product with V1.4 date-aligned splits

V1.4 (`docs/gbdt/V1.4_date_aligned_splits_plan.md`) introduces `split.mode: date_aligned` with universe-level calendar windows. Scout phase needs to know which segment it scores on.

| Option | Scout-segment in date-aligned mode | Pros | Cons |
|---|---|---|---|
| **D10.A** | Scout scores on the same val + eval segments as iter_0. | Coherent with the loop's segment semantics | Scout's "eval" is identical to loop's "eval" — risk of light double-dipping if scout winner influences iter_0 |
| **D10.B** | Scout scores on a CARVED sub-window of train (mini-eval inside train), preserving val + eval for the loop. | No double-dipping | Smaller scout-eval = noisier; cell-5 win was on the full eval |
| **D10.C** | Trailing mode: scout uses the loop's val + eval (D10.A semantics). Date-aligned mode: scout uses a mini-eval inside train (D10.B semantics). | Different by mode | Inconsistent behavior across modes |
| **D10.D** | Spec-overridable: `backend.scout.segment ∈ {loop_eval, train_subwindow}`. | Maximum flexibility | More knobs; risk of misconfig |

Sub-question: does the scout output's `eval_R_p_at_K` value become a row in `r_precision_at_k.csv`? If yes, it carries calendar-window provenance (V1.4 8-column row); if no, it stays in `metrics.json::scout` only. Cleanest answer is "no — scout is internal; only the finalized model's `predictions/test.csv` makes it to the canonical CSV."

## 6. Acceptance criteria

- **A1 — Scout phase emits structured output.** `metrics.json::scout` carries `(grid_spec, n_configs, configs[], winner_idx, runtime_seconds)`. `scout/scout_results.jsonl` exists with one row per config.
- **A2 — Iter_0 uses scout winner.** `iterations.jsonl[0].hp` matches the scout winner's HPs (modulo pinned HPs).
- **A3 — Cell-5 PASSES (the strong gate).** Under Option B with `backend.scout.enabled: true`, cell-5's `metrics.json::headline_test::R_precision_at_K[1] ≥ 0.75` (above V1.3 Option A's 0.7143). Stretch: ≥ 0.78 (within 6% of manual ceiling 0.8286).
- **A4 — Cells 1+3 regression test.** Per [_225](_225_cells13_methodology_replication.md), manual methodology FAILS on cells 1+3 — they're strong-AUC cells where defaults dominate. Acceptance: scout-enabled cell-1 + cell-3 must NOT regress vs V1.3 Option A's outcome on those cells by more than 5% on test R-p@1. (We are NOT asking scout to beat sweep on cells 1+3 — that would require a backend change per _225.) If A4 fails, D8 (scout-disable conditions) is wrong and the plan returns to design.
- **A5 — Rare-event regression.** One rare-event cell (sweep R-p@1 ≤ 0.1; e.g. `sp500_up_20pct_5d_dd5pct`) runs with scout enabled; final test R-p@10 must NOT regress vs V1.3 Option A by more than 5%. (Rare-event cells are where the L2 grid plateau winner — mcw=10 — actually works per rule 7.)
- **A6 — Scout runtime is bounded.** Total scout wall-clock ≤ 2× the cost of a single iter_0 train (D3 cap enforced). Per-config fit times logged.

A3 is the headline; A4 + A5 are the regression-prevention gates. Failing A3 means scout didn't add value on the cell it was designed for; failing A4/A5 means scout broke cells it shouldn't have touched.

## 7. Migration

- **Default OFF for backward compat.** `backend.scout.enabled: false` is the default. Existing specs (38+ trailing-anchor specs, V1.3 Option A validated specs) continue running as before.
- **Opt-in via spec block:**
  ```yaml
  backend:
    scout:
      enabled: true
      grid: depth_eta_cs_mcw  # or another preset per D1
      oracle: eval_r_precision_at_1  # per D2
      n_configs_cap: 27  # per D3.B
      wall_clock_cap_minutes: 5  # per D3.A
  ```
- **Document on/off behavior in EXPERIMENT_SPEC.md and SKILL.md.** When to opt in: anti-AUC cells (`anti_auc_flag == "true"` in canonical CSV); when to leave off: rare-event cells (rule 7 — L2 grid works), strong-AUC cells (rule per _225 — defaults dominate, scout has nothing to add).
- **No flip to default-ON in V1.3.** Default flip is V1.5_TBD candidate, gated on:
  - 10+ cells with `anti_auc_flag == "true"` validated under scout.
  - Aggregate evidence that scout doesn't regress non-anti-AUC cells.
  - Decision on whether scout-as-data-source for cross-cell analysis warrants always-on.

## 8. Risks + mitigations

| Risk | Mitigation |
|---|---|
| **Scout runtime balloons on CatBoost** | D3 wall-clock cap; per-config fit timeout sub-question in D3 |
| **Scout winner is the degenerate sink (cell-5 anti-AUC pathology fires in scout instead of in loop)** | D9.D (discard scout, fall back to defaults, flag as "scout-degenerate") |
| **Scout oracle (D2) over-fits to noise** — Q_days × 1 pick/day = small sample (cell-5 had 70 test days × R_q variable) | D2.B (use K=10 instead of K=1) OR D2.E (composite); empirical via A3+A4 |
| **Scout regresses strong-AUC cells where defaults dominate** | D8 skip-condition; A4 acceptance test catches this |
| **Scout-grid (D1) becomes outdated** as new cells discover other knob regimes | Grid spec is spec-driven (per-cell or per-preset); update with new findings without runner code change |
| **Scout doubles the smoke-test wall-clock** | D8.A's "always opt in via spec" leaves smoke tests unaffected; CI uses no-scout default |
| **Eval-segment double-dipping** (scout's eval becomes loop's iter_0 starting envelope; loop's eval R-p@K then ranks the same config that scout picked) | D10.B (scout on train sub-window) for the strict no-double-dip semantics; D10.A is OK for practical use because scout's "eval" influence is via HP selection, not direct prediction reuse |
| **Scout doesn't help and we ship more machinery for no win** | A3 + A4 + A5 are honest gates; if A3 fails, plan goes back to design |
