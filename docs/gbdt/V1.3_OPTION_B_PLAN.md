## 1. Motivation

### 1.1 What V1.3 Option A solved — and what it didn't

V1.3 Option A (the eval-R-p@K + anti-AUC-flag bundle, PR #112/#220) closed the **observability** gap on anti-AUC + strong-top-1 cells: the agent now reads `eval_r_precision_at_k`, sees the `anti_auc_flag`, gets a `degenerate_sink_warning`, and the runner auto-disables the L1 tie-break + val_brier auto-plateau on flagged cells. Cell-5 A4 validation hit R-p@1=0.7143 (above the 0.6714 sweep-baseline PASS floor; below the manual track's 0.8286 ceiling) via the in-loop calibrated oracle path in PR #115.

**The gap that remains is cold-start.** Iter_0 still launches from the default HP envelope. For CatBoost that's depth=6 + lr=0.05 + ~1000 iters; for XGBoost it's depth=6 + eta=0.3 + no early-stopping + n_estimators=100. On anti-AUC cells like cell-5 — where the winner is a **6-tree, max_depth=2 XGBoost (≤24 leaves, val_brier RIGHT at baseline)** — the default starting envelope is structurally wrong. Even with Option A's observability, the loop's per-iter HP step (`hp_changes`) walks one knob at a time from a wrong starting point; the tiny-model regime is many synchronous-knob steps away and the loop's `max_iterations: 16` cap may not be enough to reach it.

### 1.2 The cell-5 cliff (quantified)

| Track | Test R-p@1 | vs sweep | Mechanism |
|---|---:|---:|---|
| Sweep (CatBoost defaults, untuned) | 0.6714 | (baseline) | CatBoost defaults sit in a structurally-OK regime for this cell |
| Agent loop pre-V1.3 (mcw=10, γ=1) | 0.5429 | **−19%** | Heavy reg pushed toward the degenerate sink |
| V1.3 Option A loop (`_223` revalidation) | 0.7143 | +6.4% | In-loop calibrated oracle saves the run; still below sweep+24% manual ceiling |
| **Manual track ([_211](_211_cell5_manual_tuning_xgb.md))** | **0.8286** | **+24%** | 6-tree depth-2 XGBoost, eta=0.1 + ES=30, FS=top-130 |

The manual workflow had a **scout phase** (stage 2 of the 5-stage methodology — single-knob response curves across 8 knobs, ~35 fits, mapping val_brier × eval R-p@K before committing to a mix-and-match). The cell-5 winner emerged from THAT scout: the response curves showed `depth=2/3` was the inverted-U minimum, `eta=0.1+ES` was the sweet spot, and `gamma/alpha` curves descended to the degenerate sink (so they were ruled out). Without the scout, the manual track would have iterated from the wrong defaults too.

### 1.3 The N=3 evidence — be humble about what scouting solves

The cell-5 manual methodology was applied to cells 1+3 in [_225](_225_cells13_methodology_replication.md). It **FAILED on both** — cell-1 manual peaked at 0.6600 vs sweep 0.800 (−14 pts); cell-3 at 0.4267 vs sweep 0.600 (−17 pts). The dominant gap on cells 1+3 was **XGBoost-vs-CatBoost backend choice**, not anything FS/HP could close. The 5-stage methodology only works when the loop's val_brier objective is misaligned (rule 10 precondition — `anti_auc_flag == "true"`); on strong-AUC cells like cells 1+3, the methodology cannot even MATCH the un-tuned sweep baseline.

**Implication for Option B's acceptance criteria**: the scout phase must NOT be evaluated against "matches manual baselines on strong-AUC cells 1+3" — because the manual baselines themselves don't beat sweep on those cells. The scout's value lives in cells where rule 10's precondition holds (anti-AUC + strong-top-1). Acceptance bands need to reflect this: cell-5 is the strong gate; cells 1+3 are regression gates (Option B must NOT regress them, but neither must it match an unreachable target).

### 1.4 What Option B operationalizes

Stage 2 of the manual 5-stage methodology — **single-knob response curves before iter_0** — codified into the runner. Plus FS-prefit (stage 1 of the manual methodology) and a combine phase (stage 3) that lets the agent compose mix-configs from scout's per-knob curves. Iter_0 starts from the combine winner's HPs + the FS-prefit cliff-cut feature pool.

## 2. Goals + non-goals

### 2.1 Goals

- **G1**: Eliminate the "wrong starting depth" pathology on cells where the manual scout would have found a structurally-different regime. Concrete target: cell-5 R-p@1 ≥ 0.75 (above V1.3 Option A's 0.7143; within 10% of the manual 0.8286 ceiling).
- **G2**: Match or beat the V1.3 Option A loop's outcome on cells where rule 10's precondition holds (`anti_auc_flag == "true"`). NOT cells where scout has nothing to add (rule 10 doesn't apply; loop already converges from defaults).
- **G3**: Don't regress cells where the loop already does well — specifically cells with `anti_auc_flag == "false"` (rare-event cells, strong-AUC cells) where defaults are already in a structurally-good regime per N=3 evidence in [_225](_225_cells13_methodology_replication.md).
- **G4**: Keep the inner-loop iteration budget bounded — scout runtime + combine wall-clock cap-bounded per D3a/D3b, total `/gbdt-experiment` wall-clock cap-bounded by `prefit + scout + combine + max_iterations × iter_train_cost`. No unbounded scout.
- **G5**: Surface scout + combine outputs in `metrics.json` for cross-cell comparison (response surface shape becomes data).

### 2.2 Non-goals

- **NG1**: Don't replace the inner FS+HP loop. Option B is a Phase 1.4 + 1.5 + 1.6 addition before iter_0 — Phase 2 + Phase 3 + Phase 4 (calibration) + Phase 5 (artifacts) are unchanged.
- **NG2**: Don't add a backend. Still CatBoost + XGBoost only. Scout uses the spec's declared backend.
- **NG3**: Don't change V1.3 Option A's observability. `eval_r_precision_at_k`, `anti_auc_flag`, `degenerate_sink_warning`, `weighted_base_rate_brier`, `eval_segment_size` stay as-is in the iter bundle. Scout adds new fields IN ADDITION TO these.
- **NG4**: Don't ship an adaptive scout (Bayesian, multi-armed-bandit, sequential model-based). The scout is a one-shot single-knob sweep + agent-driven combine; adaptivity is V1.5 territory (parked in §9).
- **NG5**: Don't ship per-fold scout. Walk-forward currently runs 1 fold (`Fold.train_idx + val_idx + eval_idx + test_idx`); the scout runs on that one fold. Multi-fold scout is V1.5.
- **NG6**: Don't auto-tune the scout grid. The grid is fixed at runner defaults; spec can override per-knob values + caps only.

## 3. Scope

The scout + FS-prefit + combine phases fit between Phase 1 (data build) and Phase 2 (iter_0) in `/gbdt-experiment`'s lifecycle. Concretely:

```
Phase 0   — Infrastructure preflight (V1.4 cache-currency + WAL + disk)
Phase 1   — Data build (universe panel + features.build_feature_matrix + target carve)
Phase 1.4 — FS PREFIT (D11) — default-HP fit → importance → cliff-cut at < 1% of top → ~130 features
Phase 1.5 — SCOUT — 8 single-knob curves × ~4–5 values + defaults as zeroth config = ~41 fits
Phase 1.6 — COMBINE
            • agent_file_protocol mode: agent reads scout → proposes ≤50 mix configs
              → runner fits → agent picks (speed-biased prompt)
            • default mode: runner auto-composes via lexicographic per-knob argmax (no fits)
Phase 2   — Iteration 0 starts from combine output's HP + FS-prefit feature set
Phase 3   — FS+HP loop (iter 1 .. max_iterations) — unchanged (Q4.B applies — only
              agent_file_protocol can reset feature pool)
Phase 4   — Calibration — unchanged
Phase 5   — Artifact emission — unchanged + new scout/ subdir per D7
```

### 3.1 Scout mechanics (Phase 1.5)

For each knob in the locked grid (8 knobs × ~4–5 values each = ~40 single-knob configs + 1 defaults zeroth config = ~41 configs total):

1. Fit the backend (one fit; no FS pruning beyond Phase 1.4 prefit; feature pool = FS-prefit cliff-cut output).
2. Score `val_brier`, `train_brier`, `eval_R_p_at_{1,3,5,10,20}`, `train_val_gap`, `spiegelhalter_z`, `fit_seconds`, `status`.
3. Record the row in `scout_results.jsonl`.

**No runner-side oracle pick at scout time.** Scout emits everything; the combine phase (Phase 1.6) is where the oracle is applied — either by the agent (agent_file_protocol) or by the runner via lexicographic per-knob argmax (default).

Single-knob curves vary one knob at a time around the defaults baseline. This is NOT a Cartesian product — at ~40 fits total, it's tractable; an 8-way Cartesian would be ~80,000 fits.

### 3.2 What the scout does NOT do

- It does NOT run FS. FS happens upstream in Phase 1.4 (FS-prefit cliff-cut).
- It does NOT iterate. Each config is one fit, one score, done.
- It does NOT pick the final model. The combine winner is iter_0's starting envelope; the loop still does FS+HP refinement on top.
- It does NOT pick at scout time. Scout emits raw data; combine picks.
- It does NOT bypass V1.3 Option A. The anti-AUC flag + eval R-p@K + degenerate-sink warning still flow through every iter bundle.

### 3.3 FS-prefit (Phase 1.4) mechanics — NEW

The cell-5 manual workflow had an FS-prefit step before the response-curve scout: train one default-HP fit, sort features by importance, drop everything below a 1% cliff-cut, then scout on the kept feature subset (~130 of 279 features for cell-5).

- **Q1.A — How**: Train one default-HP iter_0-equivalent fit on the full feature matrix.
- **Q2.A — Cliff cut**: Drop features with importance < **1% of the top feature's importance** (matches cell-5's `_211` manual workflow; ~130 of 279 kept).
- **Q3.A — Backend**: Use the spec's declared backend for the FS-prefit (one method per backend). CatBoost uses native gain importance; XGBoost uses gain importance.
- **Q4.B — Reset policy**: Drops are **permanent in default mode**. In `agent_file_protocol` mode, the agent can issue `hp_changes.feature_pool: reset` to recover dropped features. This matches the existing loop's pool-reset semantics.

The kept-feature list is cached at the universe-snapshot level (D6.2.A) keyed by `default_hp_sha256` so the same prefit isn't recomputed across sibling cells. Cache payload is a ~1 KB JSON of `{feature_name: importance}` sorted descending.

### 3.4 Combine phase (Phase 1.6) mechanics — NEW

Combine is where the oracle is applied. The mode determines whether the agent or the runner picks.

#### 3.4.1 `agent_file_protocol` mode: TWO new exit-resume cycles before iter_0

1. Scout completes → runner exits with `scout_bundle.json` + `scout_results.jsonl`.
2. Agent reads scout output → writes `combine_decision.json` with N ≤ 50 mix configs (`{configs: [{hp: {...}}, ...]}`). The auto-composed lexicographic-argmax is **always** the agent's zeroth candidate (the runner pre-fills it into `combine_request.json` so the agent has a "vs auto-compose" comparator visible without having to compute it).
3. Runner resumes, fits each mix config (cap = 50, ~2 min/config = ≤100 min wall-clock), exits with `combine_results.json`.
4. Agent reads `combine_results.json` → writes `iter_0_decision.json` with the winning HP (one config from the mix-config list, scored by the agent's choice of oracle — the speed-biased prompt + lexicographic guidance steer toward eval R-p@1).
5. Runner resumes, starts iter_0 from the agent's HP + FS-prefit kept-feature set.

#### 3.4.2 `default` mode: NO exit-resume — runner auto-composes lexicographically

For each knob in the scout grid, the runner picks the value that maximizes the lexicographic oracle:

```
eval_R_p_at_1 > eval_R_p_at_3 > eval_R_p_at_5 > eval_R_p_at_10 > eval_R_p_at_20
```

That is, per knob, pick the value with the highest `eval_R_p_at_1`; break ties by `eval_R_p_at_3`; then `eval_R_p_at_5`; etc. The composed config (one knob value per knob) becomes iter_0's `hp_starting`. **No additional fits in combine in default mode** — this is pure runtime arithmetic on the scout results.

If the composed config equals the defaults zeroth config (i.e. no knob improved on defaults), iter_0 starts from defaults — equivalent to scout-disabled behavior, but with the scout data preserved in metrics.json for diagnostics.

#### 3.4.3 `sweep` mode: combine hard-OFF

Sweep mode is the cross-cell untuned baseline. It runs scout (so the response-curve data is captured for diagnostics) but does NOT run combine — iter_0 uses defaults. No opt-in path; sweep stays untuned per design. (Rationale: sweep's value is "what do defaults do across cells?"; tuning during sweep contaminates the cross-cell comparator.)

### 3.5 Speed-biased agent prompt — NEW

In `agent_file_protocol` mode, `combine_request.json` includes this paragraph verbatim:

> Prefer configs that train fast — favor shallow `max_depth ∈ {2, 3}`, higher `eta` with early stopping (`eta ≥ 0.1` + `early_stopping_rounds: 30`), smaller `n_estimators`, lower `colsample_bytree ∈ {0.3, 0.4, 0.5}`. The cell-5 winner was a 6-tree depth-2 fit in 3 seconds; aim for similar leaf budgets unless scout data argues otherwise.

This codifies the rule-12 doctrine ("don't dismiss tiny models on top-1 metrics") at the prompt level so the agent doesn't have to re-derive it per cell. The agent can override based on scout evidence (e.g. if the depth-2 curves on this cell are flat at baseline and depth=6 has a clear R-p@1 lead, follow the data).

## 4. Locked decisions (D1–D12)

All decisions resolved 2026-06-04. Each subsection captures the lock + the rationale paragraph.

### D1 — Knob grid: 8 single-knob curves, ~4–5 values each (LOCKED)

**LOCKED**: 8 knobs × ~4–5 values each = ~40 single-knob configs + 1 defaults zeroth = ~41 fits/cell.

**Grid values** (XGBoost knob names; runner translates to CatBoost):

| Knob | Values |
|---|---|
| `max_depth` | {2, 3, 4, 6, 8} |
| `eta` | {0.01, 0.05, 0.1, 0.2, 0.3} |
| `colsample_bytree` | {0.3, 0.4, 0.5, 0.7, 1.0} |
| `min_child_weight` | {1, 5, 10, 25} |
| `gamma` | {0, 0.1, 0.5, 1.0} |
| `alpha` | {0, 0.1, 0.5, 1.0} |
| `subsample` | {0.5, 0.7, 0.85, 1.0} |
| `scale_pos_weight` | {1, sqrt(neg/pos), neg/pos} |

#### 4.1 Backend translation table

| XGBoost knob | CatBoost equivalent | Notes |
|---|---|---|
| `max_depth` | `depth` | direct |
| `eta` | `learning_rate` | direct |
| `colsample_bytree` | `rsm` | direct |
| `min_child_weight` | `min_data_in_leaf` | direct |
| `gamma` | (no direct map) | **CatBoost grid omits this knob** |
| `alpha` | `l2_leaf_reg` | semantic-similar regularization |
| `subsample` | `subsample` | CatBoost has both `subsample` and `bagging_temperature`; use `subsample` directly |
| `scale_pos_weight` | `class_weights` | serialize as `{0: 1.0, 1: ratio}` |

**Rationale**: Cell-5 manual evidence (_211 stage 2) swept 8 single-knob curves. The Cartesian-product alternatives (D1.A's 81 configs, D1.B's 27) miss the structural insight: single-knob curves DISAGGREGATE the response surface — when depth's curve shows a sweet spot at 2 and eta's curve shows a sweet spot at 0.1 INDEPENDENTLY, the combine phase composes them; you don't need to fit all 81 combinations. The 8-knob sweep at ~40 fits is cheaper than a 4-knob 81-cell Cartesian AND covers more dimensions. Cell-1+3 evidence (_225) showed eval ordering on individual knobs was unreliable as a per-knob oracle on strong-AUC cells; the combine phase (D12) is where the oracle is applied, not at scout time, so per-knob noise doesn't decide the winner directly.

### D2 — Scout output: emit everything, no runner-side pick (LOCKED)

**LOCKED**: Scout records per-config: `knob_name, knob_value, val_brier, train_brier, eval_R_p_at_{1,3,5,10,20}, train_val_gap, spiegelhalter_z, fit_seconds, status ∈ {"ok", "timeout", "error"}`. **No runner-side oracle pick at scout time.**

**Rationale**: D2's open-question framing — "which metric picks the winner?" — turned out to be the wrong question. Scout's job is to map the response surface; combine's job is to pick. Separating them means: (a) the agent in agent_file_protocol mode sees ALL the data including the train_brier + train_val_gap + Spiegelhalter Z that signal the degenerate sink, not just a runner-chosen oracle; (b) the default-mode lexicographic auto-compose has the full R-p@K vector available for tie-breaking; (c) the cross-cell mining use case (D7's data dump) gets a richer scout dataset to learn from over time.

### D3a — Per-config + soft wall-clock scout cap (LOCKED as D3a.C)

**LOCKED**: Per-config fit-timeout: 30 s XGBoost, 120 s CatBoost (configs hitting timeout: `status = "timeout"`, excluded from oracle). Soft wall-clock cap: 5 min XGBoost, 30 min CatBoost. Configs queued past cap are dropped in submission order.

**Rationale**: D3.D ("no cap") risks unbounded CatBoost runtime; D3.B ("N-config cap only") doesn't bound wall-clock. The locked compound cap gives both predictability (wall-clock bounded) and degeneration-tolerance (a single slow-config doesn't stall the whole scout). Per-config timeout matches the cell-5 evidence: the 6-tree winner fits in 3 s; a degenerate 1000-tree config could take 60 s+; the 30 s XGBoost timeout standardizes.

### D3b — Combine cap with defaults-zeroth comparator (LOCKED as D3b.A modified)

**LOCKED**: Hard cap **50 mix configs** per combine round (~2 min/config × 50 = up to 100 min combine wall-clock). The **default-mode lexicographic auto-compose** is ALWAYS included as the agent's zeroth candidate in every combine round (forces a "vs auto-compose" comparator).

**Rationale**: A 50-config combine round is bounded but generous enough to let the agent explore mix-configs aggressively. Forcing the lex auto-compose as zeroth-candidate ensures the agent always knows "what would the runner have picked without me?" — if the agent picks something other than auto-compose, there's a visible comparator in `combine_results.json` for post-hoc review. Combined with the speed-biased prompt (§ 3.5), this rules out the failure mode where the agent over-explores deep-tree configs that take 5+ minutes each.

### D4 — Mode integration (LOCKED as C-restricted)

**LOCKED**:
- `agent_file_protocol` mode: scout + agent-driven combine.
- `default` mode: scout + runner auto-composes lexicographically (NO mix-config fits).
- `sweep` mode: scout + combine **hard-OFF** (no opt-in; sweep mode stays untuned per design).

**Rationale**: D4.A ("all 3 modes") was too aggressive — sweep mode's value depends on the cross-cell comparator being untuned defaults; tuning during sweep contaminates the comparator. D4.B ("agent only") leaves default mode + smoke tests with the cold-start problem. D4.C ("opt-in for sweep") adds complexity. The C-restricted lock gives sweep its untuned semantics (scout data is captured for diagnostics but combine doesn't run), default mode gets cold-start lift via lexicographic auto-compose (no extra fits beyond scout), and agent mode gets the full per-cell tuning path.

### D5 — What scout sets on iter_0 (LOCKED as D5.A modified)

**LOCKED**: Combine output sets iter_0's `hp_starting`. Feature pool for iter_0 = FS-prefit cliff-cut output (D11). No `feature_weights`, no sticky knobs, no D5.B/C/D semantics.

**Rationale**: D5.B's "couple scout to FS" intuition is now handled by D11's FS-prefit phase (which runs BEFORE scout). Scout sees the cliff-cut feature pool already; combine output is HP-only. D5.C's `feature_weights` is CatBoost-only and adds machinery; D5.D's sticky knobs reduces agent agency. Cleanest separation: D11 does FS, scout+combine does HP, iter_0 starts from both.

### D6 — Cache behavior (LOCKED all three sub-locks)

**LOCKED**:
- **D6.1.A**: All scout + combine configs reuse the universe feature matrix (post-FS-prefit cliff-cut, ~130 features) — single matrix, N+M fits.
- **D6.2.A**: FS-prefit kept-feature list cached at universe-snapshot level (key includes `default_hp_sha256`); ~1 KB JSON payload.
- **D6.3.A**: Per-backend feature matrix (CatBoost native categoricals; XGBoost numeric-only) — flows from #226's per-key universe cache.

**Rationale**: D6.1.A is the natural behavior; explicit lock makes the contract clear. D6.2.A means sibling cells sharing a universe snapshot don't re-pay the FS-prefit cost. D6.3.A reflects #226's per-backend cache key — adding scout doesn't change cache layout, it inherits.

### D7 — Reporting (LOCKED all three sub-locks)

**LOCKED**:
- **D7.1**: `metrics.json::scout` block (`grid_spec, backend, n_configs_total, n_configs_completed, runtime_seconds, defaults_metrics, per_knob_winner, lexicographic_auto_compose, status`) + `metrics.json::combine` block (`n_mix_configs_proposed, n_mix_configs_completed, exit_resume_rounds, agent_winner, vs_lexicographic_auto_compose`).
- **D7.2**: `scout/` subdirectory dump with: `scout_results.jsonl`, `combine_request.json`, `combine_decision.json`, `combine_results.json`, `iter_0_decision.json`.
- **D7.3.C**: **NO figures** (matplotlib-free; data lives in JSON/JSONL only).

**Rationale**: D7.A's metrics.json-only path loses the granular per-config data (jsonl is the right format). D7.B's subdir-only loses the headline scout/combine summary (metrics.json is the canonical headline). D7.C ("both") is the lock. D7.D's figures were tempting (visual response-curve panels are great for memos) but matplotlib calls in the runner add a dependency surface; the data is in JSONL so downstream memo-rendering scripts can produce figures on demand.

### D8 — Skip conditions (LOCKED as D8.A)

**LOCKED**: Always run scout unless explicitly disabled via `backend.scout.enabled: false`. No auto-skip based on `anti_auc_flag` or sweep-CSV lookups.

**Rationale**: D8.B/C/D require chicken-and-egg signals (the anti_auc_flag is computed from iter_0, which doesn't exist yet at scout time; sweep-CSV lookup requires the cell to have a prior sweep row). The simplest path is always-on (gated by the spec flag). On strong-AUC cells where scout has nothing to add, combine's lexicographic auto-compose will likely pick defaults (or very-close-to-defaults), and iter_0 starts roughly where it would have without scout — but with the scout data captured for diagnostics. The wall-clock cost is bounded by D3a/D3b.

### D9 — Failure handling (LOCKED all three sub-locks)

**LOCKED**:
- **D9.1.A**: Defaults are scout's zeroth config (auto-included; 1 extra fit; lets every cell answer "did scout improve on defaults?").
- **D9.2.A**: In **default mode** — if winner has `val_brier ≈ baseline` AND `train_val_gap ≈ 0` (degenerate-sink-warning triggers), discard scout, use defaults for iter_0, flag `metrics.json::scout::status = "degenerate_sink_fallback"`. In **agent mode** — surface warning verbatim to agent; agent decides.
- **D9.3.A**: Use partial data on D3a cap-hit; lexicographic on completed configs only; flag `n_completed / n_total` in metrics.

**Rationale**: D9.1.A makes the comparator "scout vs defaults" explicit at scout time, not just at combine time. D9.2.A handles the cell-5 anti-AUC pathology firing in scout (where the L2 regularization knobs walk toward a degenerate sink that's at-or-below the weighted base rate Brier) — in default mode, the runner discards and falls back; in agent mode, the agent gets the warning verbatim and can apply judgment (e.g. pick the depth=2 config from scout instead of the auto-composed winner). D9.3.A means the cap-hit doesn't fail the whole run; it just operates on what scout managed to complete.

### D10 — V1.4 cross-product (LOCKED both sub-locks)

**LOCKED**:
- **D10.A**: Scout scores on the **same val + eval segments as iter_0**. Honest about double-dipping (the loop already uses eval for iter_N selection); methodology-consistent.
- **D10.sub.A**: Scout is strictly internal. **NO row in `r_precision_at_k.csv`** for scout output. Only finalized models populate the canonical CSV.

**Rationale**: D10.B's "carve a mini-eval inside train" creates a different metric than the loop uses for iter_N selection — coherence with the loop matters more than perfect anti-double-dipping (the loop is the same way). The canonical CSV is the cross-cell comparator for FINAL models; scout/combine outputs are internal and live in metrics.json + `scout/` only.

### D11 — FS-prefit phase (NEW — LOCKED Q1.A + Q2.A + Q3.A + Q4.B)

**LOCKED**:
- **Q1.A**: Train one default-HP iter_0-equivalent fit → sort features by importance → cliff-cut.
- **Q2.A**: Cliff threshold = features with importance < **1% of top feature's importance** (matches cell-5 manual workflow; ~130 of 279 kept).
- **Q3.A**: Use the spec's declared backend for the FS-prefit (one method per backend).
- **Q4.B**: Pool reset is **manual only** — agent decides via `hp_changes.feature_pool: reset` in `agent_file_protocol` mode. In default mode, drops are permanent (no actor to reset).

**Rationale**: The cell-5 manual workflow had FS-prefit BEFORE the response-curve scout — the scout's response curves were on the kept feature subset, which made the depth=2/eta=0.1 winner emerge cleanly (a larger feature pool would have favored deeper trees just to model the noise features). Codifying FS-prefit as Phase 1.4 means scout sees the same conditions the cell-5 winner emerged under. The 1% cliff (Q2.A) matches what `_211` actually did; Q3.A keeps the backend consistent end-to-end (no CatBoost-prefit-feeds-XGBoost-scout situation); Q4.B's manual-reset preserves the agent's recovery path while keeping default mode simple.

### D12 — Combine phase (NEW — LOCKED)

**LOCKED**:
- **`agent_file_protocol` mode**: TWO new exit-resume cycles before iter_0 (see § 3.4.1).
- **`default` mode**: NO exit-resume; runner picks lexicographic per-knob argmax automatically and proceeds directly to iter_0 (see § 3.4.2).
- **Oracle priority (lexicographic)**:
  ```
  eval_R_p_at_1 > eval_R_p_at_3 > eval_R_p_at_5 > eval_R_p_at_10 > eval_R_p_at_20
  ```
  Applied per-knob in default mode (auto-compose), and as the agent's guidance prompt in agent mode.

**Rationale**: Combine separates the oracle from scout (D2's lock — scout records, combine picks). In agent mode, the agent reads the full scout response surface, proposes mix configs that may cross knobs in ways the per-knob argmax can't (e.g. "depth=2 + eta=0.1 + colsample=0.3" as a composed config), and the runner fits the proposed configs to verify. In default mode, lexicographic per-knob argmax is the cheapest defensible composition (no additional fits; uses scout's R-p@K vector directly). The lex priority `R-p@1 > R-p@3 > ... > R-p@20` matches the rule-10/11 doctrine: top-1 is the operating metric for portfolio top-pick use; K=3/5/10/20 are tie-breakers.

## 6. Acceptance criteria

- **A1 — Scout phase emits structured output.** `metrics.json::scout` carries `(grid_spec, backend, n_configs_total, n_configs_completed, runtime_seconds, defaults_metrics, per_knob_winner, lexicographic_auto_compose, status)`. `scout/scout_results.jsonl` exists with one row per config (per D7.2).
- **A2 — Iter_0 uses combine winner.** `iterations.jsonl[0].hp` matches the combine winner's HPs (modulo pinned HPs). In `agent_file_protocol` mode, `iter_0_decision.json` exists and is byte-consistent with iter_0's `hp_starting`.
- **A3 — Cell-5 PASSES (the strong gate).** Under Option B with `backend.scout.enabled: true`, cell-5's `metrics.json::headline_test::R_precision_at_K[1] ≥ 0.75` (above V1.3 Option A's 0.7143). Stretch: ≥ 0.78 (within 6% of manual ceiling 0.8286).
- **A4 — Cells 1+3 regression test.** Per [_225](_225_cells13_methodology_replication.md), manual methodology FAILS on cells 1+3 — they're strong-AUC cells where defaults dominate. Acceptance: scout-enabled cell-1 + cell-3 must NOT regress vs V1.3 Option A's outcome on those cells by more than 5% on test R-p@1. If A4 fails, D8's "always run scout" is wrong and the plan returns to design.
- **A5 — Rare-event regression.** One rare-event cell (sweep R-p@1 ≤ 0.1; e.g. `sp500_up_20pct_5d_dd5pct`) runs with scout enabled; final test R-p@10 must NOT regress vs V1.3 Option A by more than 5%.
- **A6 — Scout runtime is bounded.** Per-config + soft wall-clock caps (D3a) enforced; partial-completion fallback (D9.3) works on cap-hit.
- **A7 — Combine wall-clock is bounded.** Scout + combine wall-clock ≤ 110 min/cell in agent_file_protocol mode (5 min XGBoost scout + 100 min combine cap + FS-prefit ~5 min); ≤ 10 min/cell in default mode (5 min XGBoost scout + ~0 min combine since lex auto-compose is arithmetic + FS-prefit ~5 min). Per D3a/D3b caps + D11's 1 prefit fit.

A3 is the headline; A4 + A5 are the regression-prevention gates; A6 + A7 are the wall-clock gates. Failing A3 means scout didn't add value on the cell it was designed for; failing A4/A5 means scout broke cells it shouldn't have touched; failing A6/A7 means the locked caps don't actually bound runtime.

  - 10+ cells with `anti_auc_flag == "true"` validated under scout.

## 8. Risks + mitigations

| Risk | Mitigation (locked) |
|---|---|
| **Scout runtime balloons on CatBoost** | D3a.C — per-config 120 s timeout + 30 min soft wall-clock cap |
| **Combine wall-clock balloons in agent mode** | D3b.A modified — 50 mix-config hard cap + speed-biased prompt biases toward 3-second tiny-model fits |
| **Scout winner is the degenerate sink (cell-5 anti-AUC pathology fires in scout)** | D9.2.A — default mode discards + falls back to defaults; agent mode surfaces warning verbatim for judgment |
| **Eval-segment double-dipping** (scout's eval = loop's iter_0 eval) | D10.A — accepted; methodology-consistent with the loop's existing eval-segment use; mitigated by acknowledging the limitation in `metrics.json::scout::caveats` |
| **Strong-AUC regression** (cells 1+3 where scout has nothing to add) | A4 acceptance gate (≤ 5% regression on test R-p@1); D8.A's "always run" is acceptable because lex auto-compose likely picks defaults on these cells |
| **Scout-grid becomes outdated** as new cells discover other knob regimes | Grid is spec-overridable per-knob (§ 7 migration block); no code change to add a value |
| **Scout doubles smoke-test wall-clock** | D8.A's "always opt in via spec" leaves smoke tests unaffected; CI uses `scout.enabled: false` default |
| **Scout doesn't help and we ship more machinery for no win** | A3 + A4 + A5 are honest gates; if A3 fails on cell-5, plan goes back to design |
| **Agent over-explores deep-tree configs in combine** | Speed-biased prompt (§ 3.5) + 50-config cap + lex auto-compose visible as zeroth candidate |
| **Cache invalidation on FS-prefit** | D6.2.A — kept-feature list keyed by `default_hp_sha256`; spec change to defaults → cache miss → re-prefit; correct by construction |
