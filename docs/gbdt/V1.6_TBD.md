## Performance (compound with what shipped)

1. **Phase 1c — batch-per-family pass reduction.** The remaining manual per-ticker
   `.xs` loops still walk one pass per ticker: `_obv_N` (cumsum), `_vol_ret_corr_N`
   (rolling corr), `beta_N` (rolling cov/var). V1.6 cut the *biggest* offenders
   (F16-meta 93→1, native `groupby.rolling`), but ~150 passes remain and their fixed
   split/combine overhead (~0.64 s/pass on 962k rows) is what **caps the incremental
   extend at ~1.3×**. Reducing the pass count lowers that floor — it compounds with
   the cache (the extend gets closer to "seconds") and speeds every full build too.
   Standalone gain is diminishing (~1.2–1.4×); its real value is unblocking the cache.

2. **[DONE] S2 — parallelize the seed** (`--jobs N`; the daily cadence uses `--jobs 8`).
   `_cmd_seed` runs `fetch_with_meta` through a `ThreadPoolExecutor` — safe because the
   per-DB write lock (`cache._get_lock`, WAL) serializes writes and each ticker is
   independent (test: concurrent 3-ticker seed, no clobber). **Measured 474 s → 269 s
   (1.76×)** on the full sp500 — but that run was a no-gap no-op (fresh cache), so it
   measured the **GIL-bound `read_processed` + `detect_gaps` floor**, not the network
   fetch. A real fetch-heavy daily-advance seed (507 new-bar fetches) parallelizes
   better (network releases the GIL); the clean end-to-end number awaits a stale-cache
   day.
   - **2a follow-up — read-tail for gap detection.** `read_processed` loads a ticker's
     FULL history (~9k rows) just to detect a 1-day gap → ~0.9 s/ticker even with zero
     fetch. Reading only the recent tail would slash the no-op seed and lift S2's
     ceiling. A `data_pipelines` optimization.

3. **The fixed costs *around* the build dilute the cache to ~1.1× end-to-end.** On the
   full sp500, `build_scores` ≈ **418 s full → 385 s extend (only 1.1×)** because the
   feature build is only *part* of it; three fixed costs the cache doesn't touch:
   - **(3a) full-matrix predict.** `_build_one` predicts the WHOLE matrix (~962k rows)
     even on an extend; only the **test window (for the self-check) + the new dates**
     are needed → predict ~30× fewer rows. *Biggest lever of the three.*
   - **(3b) full-matrix save.** `build_or_extend` rewrites the entire matrix parquet
     (~30 s on sp500) every extend, eating much of the build saving. Save less often, or
     an append-friendly store.
   - **(3c) load-avoidance.** `load_panel` (~31 s) runs every day. Persist the panel
     **tail** + read only new bars (`_cache_read(t, cached_max_date, end)` per ticker).
   Until 3a–3c land (and Phase 1c cuts the build's own per-pass floor), the incremental
   cache's daily payoff is marginal — its clean win is the **weekly full run + the
   experiment loop**, where the build dominates and the fixed costs are amortized.

## Correctness / robustness

4. **Eligibility "add-ticker" fast path.** Phase 4 falls back to a full rebuild when a
   ticker crosses the 1,600-row floor (`_require_stable_membership` → `SeamMismatch`).
   A ticker crossing is rare (~once in its lifetime), so the fallback is cheap in
   expectation; a targeted "add just that column + re-rank the affected cross-sections"
   path is possible but low priority.

5. **Rolling higher-moments ~1e-4.** The extend matches a full build to ~1e-4 on
   `returns_skew`/`returns_kurt` (pandas' online rolling rounds differently by offset).
   Validated harmless (`p_raw` max|Δ| = 0 through the tree model). If a future model or
   metric ever became sensitive at 1e-4, either recompute F8 always-full or route those
   two families through a numerically-stable rolling. Not needed now.

## Reach

6. **Wire the cache into the gbdt experiment loop.** Only the backtest inference path
   (`infer_fresh_predictions`) uses the incremental cache. The agent-loop rebuild
   (`gbdt/__main__.py`, ~3 h/cell on sp500 per `feature_cache.py`) uses the exact-match
   `feature_cache`; on a grown panel it could `build_or_extend` instead.

7. **Live daily-cadence wall-time.** The V1.6 timings are isolated spot-checks (build
   279→209 s; extend ~1.3×; seed split 60→14 min). Measure the *live* end-to-end
   (seed + extend + gate + append) once a genuinely new complete trading day is
   available — implementation landed on 2026-07-02, whose bar was still intraday.
