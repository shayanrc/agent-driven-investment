# gbdt V1.8 — F19 revenue-growth features + lattice sweep

## Goal

Add a **revenue-growth** feature family (F19) to the opt-in fundamentals surface and
map where it helps across the 17-cell sp500 lattice, on both backends. F18 (`_272`–`_278`)
covered valuation *levels* (yields) + one log-YoY growth column; the hypothesis here is
that **rate-of-change of the top line** (accelerating/decelerating revenue) is a distinct,
possibly stronger signal than the valuation level.

Requested by the user (2026-07-06): "features for yoy quarterly sales/revenue growth %,
ttm sales/revenue growth as well and do a sweep" + "Add single quarter QoQ as well. If
it's bad FS should drop it."

## Feature family — F19 (12 columns)

Four growth measures, each emitted as {level, `_xs_rank`, `_xs_zscore`} — the F18 idiom
(asset-agnostic, universe-relative), all in **percent** form (simple ratio − 1, unlike the
existing F18 `fund_rev_ttm_yoy` which is log):

| base column | definition | reads |
|---|---|---|
| `fund_rev_q_yoy` | single-quarter revenue YoY: `rev_q(t)/rev_q(t−252) − 1` | seasonality-safe, most responsive |
| `fund_rev_ttm_yoy_pct` | TTM revenue YoY %: `rev_ttm(t)/rev_ttm(t−252) − 1` | smooth (percent twin of the F18 log col) |
| `fund_rev_ttm_qoq` | TTM sequential QoQ %: `rev_ttm(t)/rev_ttm(t−63) − 1` | acceleration, seasonality-safe |
| `fund_rev_q_qoq` | single-quarter sequential QoQ %: `rev_q(t)/rev_q(t−63) − 1` | seasonal; kept deliberately — if dead, FS drops it |

- **`_xs_rank`** = cross-sectional percentile across the panel that date; **`_xs_zscore`**
  = cross-sectional z-score that date (magnitude). Same `_xs_zscore` helper as F7/F14/F18.
- **Causality (C1):** each value at `t` uses only filings with `filed_date ≤ t`; the
  YoY/QoQ shifts are strictly trailing (252-td / 63-td, the F18 idiom); ranks are
  same-date. Extended into the fundamentals-perturbation leakage test.
- **`_FUND_CHG_LOOKBACK` / `_FUND_GROWTH_LOOKBACK`** reused (63 / 252 td) — the same
  constants the F18 `fund_earnings_yield_chg_63` / `fund_rev_ttm_yoy` use.
- Non-positive / NaN denominators → NaN (the F18 `_safe`-style guard); no winsorizing
  (consistent with F18 — `_xs_rank` is outlier-robust, `_xs_zscore` mirrors F18's).

### The single-quarter-QoQ note

Raw single-quarter QoQ is dominated by seasonality (Q3→Q4 up, Q4→Q1 down for most
sectors) and is a weak growth signal on its own. It is included **at the user's explicit
request** as a test of the FS step: if it carries no gain, importance-based pruning drops
it — and a pruned-everywhere column is itself a clean negative result (contrast: all 13
F18 cols survived FS in `_275`/`_276`).

## Token design — F18 stays frozen

New candidates token **`all_fundamentals2`** = F1–F16 (279 technical) + F18 (13) + F19 (12)
= **304 cols**. The existing `all_fundamentals` (F18, 292 cols) is **unchanged and
byte-identical** — `_272`–`_278` stay reproducible. F19 fires only via the new token or an
explicit `F19` in a `candidates` list. Not in the default `all`.

## Data-layer prerequisite — single-quarter revenue in the valuation panel

F19's quarterly measures need **single-quarter** revenue (the YoY/QoQ base), which the
valuation panel does not currently expose (only `revenue_ttm`). The single-quarter
`revenue` is already present upstream in `us_fundamentals` (de-YTD'd to true per-quarter
values) and flows into `build_ttm_timeline`. Change:

- `valuation.ttm.build_ttm_timeline`: emit `revenue_q` = the newest quarter's single
  revenue for each valid trailing-4Q window (same causal `effective_date` grid as
  `revenue_ttm`; NaN where the window is invalid).
- `valuation.panel.PANEL_COLUMNS`: add `revenue_q`.
- `gbdt.data._FUND_FEATURE_COLS`: add `revenue_q` so it reaches `fund_df`. (F18's
  `fundamentals_features` reads only its own columns, so this does not perturb F18.)
- Regenerate `results/valuation/data/valuation_panel.parquet`. The existing columns stay
  value-identical (only `revenue_q` is added; TTM/ratio math unchanged; all split-having
  tickers are already in `split_factors.parquet` so share adjustment is unchanged).
  Verified in Phase C on the overlapping date range.

## Sweep design (Phase D)

- **Cells:** the full 17-cell sp500 lattice (the `_274` canonical set).
- **Arms:** `all_fundamentals` (F18) vs `all_fundamentals2` (F18+F19) — the marginal-F19
  test — matched single-fit (identical HP, `max_iterations: 1`; only `candidates` differs;
  the `[[project-gbdt-macro-features-f17]]` clean-A/B rule).
- **Backends:** both xgboost and catboost (`_278` established CatBoost as the robust
  backend on these cells; xgboost for continuity with `_272`–`_276`).
- **Window:** date_aligned `train_start: 2019-01-01` (window 1, the `_274` window, so the
  `_274`/`_278` technical + F18 rows are reusable as context). Snapshot pinned.
- ~68 fits (17 × 2 × 2), background + heartbeats, disk/no-competing-run preflight.
- **Window-2 confirmation (Phase F):** any cell where F18+F19 beats F18 on window 1 gets
  the independent date_aligned window-2 (`train_start: 2019-07-01`, test 2025-H1 — the
  `_278` pattern) before it is called a candidate. Bulk metrics don't see the top-book
  tail (`_276`), so a one-window win is not a result.

## Verdict criteria

Per cell: does adding F19 to F18 improve **test R-Precision@K** (the top-book operating
metric) AND survive window 2? Report raw metric + base_rate, no lift columns. Record which
of the 4 growth measures FS keeps/drops per cell. No champion swap, no `/daily-predictions`
change (human decisions, `_019`).
