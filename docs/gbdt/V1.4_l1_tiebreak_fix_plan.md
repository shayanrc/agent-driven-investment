# V1.4 — L1 tie-break fix plan

**Status:** plan-review (Plans and branches per CLAUDE.md).
**Branch:** `v1.4-l1-tiebreak-fix-plan`.
**Promoted from:** `docs/gbdt/V1.3_TBD.md` item 5 (L1 tie-break general audit, #215) + `docs/gbdt/V1.4_TBD.md` item from task #240 (val_brier-flat best-iter rule coin-flips on healthy-AUC cells).

## Why now

Two separate parking-lot rows are the same code surface:

- **#215** (L1 tie-break general audit, V1.3 Option A scope-deferred). Asks whether the train_val_gap + Spiegelhalter Z tie-break logic (#187) is correct outside the anti-AUC band where V1.3 Option A auto-disabled it.
- **#240** (val_brier-flat best-iter rule coin-flips on healthy-AUC strong-top-1 cells). Surfaced by #239 (r1k +40%/100d, -12% vs sweep) and confirmed by #241 (r1k +50%/200d, -22% vs sweep). The runner's `src/gbdt/fs_hp_loop.py::best_checkpoint` (called from `src/gbdt/train.py:1228`) enters tie-break mode whenever `val_brier_range < tie_band` and then selects the iter with the *lowest* val_brier + smallest train_val_gap — which on these cells is strictly the LEX-WORST iter (lowest eval R-p@1).

The two rows have identical root cause + identical patch surface. Fold into one V1.4 plan. The #243 agent run on `nifty500_up_30pct_50d_dd15pct` (NON-strong-top-1, healthy AUC ~0.72) is in flight as the third data point — if it underperforms its sweep, the bug generalizes beyond strong-top-1; if it doesn't, scope stays bounded.

- Combine phase + scout phase did real work; finalization throws it away

## Proposed fixes (3 options, NOT mutually exclusive)

### Option (a) — eval R-p@1-best fallback in tie-break

When `val_brier_range < tie_band`, **fall back to eval R-p@1-best iter** instead of L1 (train_val_gap + Spiegelhalter Z). Rationale: eval R-p@K is the project's headline metric and the agent's stated oracle in `_211` playbook rule 11. If val_brier is uninformative (range below the noise floor), the runner should defer to the oracle.

**Pros:**
- Matches the agent's mental model + the playbook
- Cheap to implement — `best_checkpoint` already accepts `eval_r_precision_at_1s` and `train.py` already passes it; the V1.3 Option A code path at `src/gbdt/fs_hp_loop.py:240-261` already handles "tie set + eval R-p@1 fallback" on the anti-AUC branch. Option (a) is **gating the existing fallback on `not is_anti_auc AND val_brier_range < tie_band`** — ~10-15 lines that mirror the existing block onto the non-anti-AUC branch.
- Zero risk of regressing rare-event cells (eval R-p@1 ≈ val_brier on those — same iter wins both)

**Cons:**
- Eval R-p@1 is noisier than val_brier on rare-event cells with `Q_days × min(R, 1)` small samples
- If val_brier is genuinely flat AND eval R-p@1 has high run-to-run noise, the fallback could ship a noisier-but-better-on-paper iter

### Option (b) — replace L1 entirely with eval R-p@K weighted sum

Replace the L1 tie-break with `sum(weight[k] · eval_R_precision_at_k)` over `k ∈ {1, 3, 5, 10, 20}`, weights matching the lex oracle's priority (e.g. `[16, 8, 4, 2, 1]` normalized). The agent's lex oracle is `R-p@1 > 3 > 5 > 10 > 20`; the weighted sum is a continuous approximation that uses all 5 K values, avoiding strict lex ties on degenerate cells.

**Pros:**
- Single rule, no branch logic between "L1 fires" vs "L1 doesn't fire"
- Uses more information than (a)
- Aligns with combine-phase reporting (which already uses lex)

**Cons:**
- Bigger change — touches the L1 contract everywhere (`fs_hp_loop.py::best_checkpoint`, `finalize`, `report.py` headline)
- Need to validate the weights empirically (lex-equivalent for top-1-dominated cells, R-p@10-dominated for rare-event cells)
- Touches anti-AUC cells too — currently L1 is auto-disabled on those (#220), so the weighted sum must be at least as good as Option A's eval R-p@K-best behavior

### Option (c) — hard warning + manual override

Don't change the selection logic. Emit a **hard warning** in finalize when L1 picks an iter with `eval_R_p_at_1 < max(eval_R_p_at_1) - 0.05`. Let the agent override via `final_iter_override` in a new spec/decision field. Keep the runner conservative; surface the call to the agent.

**Pros:**
- Minimal change; preserves L1's existing behavior on cells where it's correct
- Aligns with V1.3's "agent is the data scientist" mental model
- The override mechanism is reusable for other "I know better than the heuristic" cases

**Cons:**
- Doesn't fix unattended sweep runs (no agent to act on the warning)
- Adds one more thing for the agent to track per iter
- The "0.05" margin is hand-picked — needs empirical justification

### Recommendation (subject to plan-review)

**Ship (a) first.** Smallest change, addresses the bug for the cells we've seen, doesn't break the L1 logic where it's working (rare-event cells with bulk val_brier signal). If the #243 result shows (a) is insufficient for non-strong-top-1 healthy-AUC cells, escalate to (b). (c) is a fallback if (a) + (b) both have empirical issues.

## Acceptance gates

Two distinct code paths after the patch lands (`is_anti_auc` branch — already in place per #220 — and the new mirrored non-anti-AUC branch). Each gate is labeled with the branch it exercises so we know that the patched logic is actually executed, not just incidentally satisfied.

| gate | cell | branch exercised | sweep R-p@1 | gate threshold | what it proves |
|---|---|---|---:|---|---|
| 1a | `russell1000_up_40pct_100d_dd20pct_aligned` (replay #239) | NON-anti-AUC (val_brier flat) | 0.550 | test R-p@1 ≥ 0.550 | new branch picks lex-correct iter when val_brier is flat |
| 1b | `russell1000_up_50pct_200d_dd25pct_aligned` (replay #241) | NON-anti-AUC (val_brier flat) | 0.737 | test R-p@1 ≥ 0.737 | same; larger-magnitude case |
| 2 | `nasdaq100_up_10pct_50d_dd5pct` (V1.3 Option A A4 cell) | **anti-AUC** | 0.671 | test R-p@1 ≥ 0.671 | #220's existing auto-disable still wins; the new gate does NOT reroute anti-AUC cells |
| 3 | `nasdaq100_up_10pct_25d_dd5pct` (the original L1 cell per #185) | NON-anti-AUC, val_brier sharp | (per `_185`) | test R-p@1 ≥ historical | L1 still fires on cells where val_brier IS informative — i.e. the patched branch's `val_brier_range < tie_band` gate keeps L1 unchanged when val_brier has real structure |
| 4 | one rare-event cell (e.g. `russell1000_up_40pct_25d_dd20pct` from the r1k trio) | NON-anti-AUC, val_brier sharp | (per #188) | test R-p@1 ≥ sweep | L1 was originally designed for rare-event cells per `_185`; new logic must not regress them |

**Why M3 matters (gate-design note).** Gate 2 alone does NOT exercise the patched code path — cell-5 routes through `is_anti_auc=true` and never enters the new fallback. Gates 1a + 1b + 3 + 4 are the ones that actually run the new code. Gate 2 is kept as a guardrail that the patch is a NEW branch, not a rewrite of the existing one.

**Branch-routing verification.** For every replay cell, the post-patch `loop/iter_*_request.json` must record `anti_auc_flag` so we can confirm which branch the finalize touched. If a cell that should hit the non-anti-AUC branch is silently routed through the anti-AUC branch (e.g. canonical CSV row missing → `anti_auc_flag="unknown"` → defaults to anti-AUC handling), the gate is INCONCLUSIVE and re-run after CSV row backfill.

**Artifact gate.** Each replay cell gets a row in `results/gbdt/data/r_precision_at_k.csv` with the post-patch values + a memo `docs/gbdt/_<id>_l1_tiebreak_fix_validation.md` cross-referencing sweep + pre-patch + post-patch.

## Out of scope

- Changing the `tie_band` default (V1.3#1 currently shipped at 0.005; the V1.4 plan keeps it).
- Touching the combine phase or scout phase logic — both did real work in #239 + #241; the issue is finalize-side.
- Multi-cell sweep runner (parked separately).
- The `--resume snapshot-end` UX gap (#231 already documented).

## Risks

- **#243's in-flight result might invalidate Option (a).** If it shows L1 picking a strictly-dominated iter on a non-strong-top-1 healthy-AUC cell, Option (a) still applies but the empirical signal is "L1 is wrong more broadly than #239+#241 implied." Plan stays valid; just larger blast radius for replays.
- **Option (a) might regress rare-event cells.** Mitigated by P5. If the replay shows regression, escalate to (c) for the bounded surface area.
- **Eval R-p@1 noise.** Use the same calibrated predictions the canonical CSV uses (#222) — DO NOT use raw predictions.
