# gbdt V1.1 — Agent-driven FS+HP loop (the user IS the data scientist sub-agent)

**Goal**: wire `src/gbdt/__main__.py::run_experiment()` to actually pass an `fs_hp_callback` into `walk_forward_train()`, where the callback delegates per-iteration FS pruning + HP tuning decisions to **the human user (or their Claude Code session) acting as the data scientist sub-agent**. No external API call. The runner emits a diagnostic bundle (`diagnose.json`) and **exits** each iteration (file-based protocol + resume checkpoint); the agent reads the bundle from disk, reasons about it as a data scientist tuning a model would, writes the decision back to disk, and relaunches the runner with `--resume`. (See § 0 for the resolved architecture — the original draft below described a block-and-poll variant that § 0 supersedes.)

This is V1.1 because v1 ships the experiment-loop infrastructure (per `docs/gbdt/V1_PLAN.md`); V1.1 ships the missing "agent" half.

## § 0. Resolved decisions (2026-05-28) — AUTHORITATIVE

The 6 open questions (originally § 14) were resolved with the user on 2026-05-28. **These supersede any conflicting description in the draft sections below** (notably §§ 2–3, 5, 7, 10, and the old § 13 entries 2/3/5):

1. **Notification = exit-and-resume + harness completion-notification** (Q1). The runner does NOT block-and-poll. Each iteration: train → emit the bundle → **exit cleanly** (writing a resume checkpoint). The harness's standard background-task completion notification reaches the agent (the user's session); the agent reads the bundle, writes the decision, and relaunches `python -m gbdt.experiment --resume <run_id>`. No long-lived blocked process; all state on disk. → adds a **checkpoint/resume** requirement to the runner (Phases 1–2).
2. **No `questions_for_user` field** (Q2). Because the runner hands control back to the agent (in the conversation) every iteration, when the agent needs the human's judgment it just asks in chat before writing the decision. Drop the field + any sentinel mechanism.
3. **No decision-wait timeout; large backstop training timeout + heartbeat logging** (Q3). Exit-and-resume removes the decision-wait entirely. The only timeout is a per-iteration *training* backstop (default ~8 h) guarding a wedged/runaway fit. Stuck-detection is via a **heartbeat** log line (separate logging PR), watched by check-ins — not the timeout. (US feature builds legitimately take ~28 min, so a short timeout is unsafe.)
4. **Phase 6 = acceptance test reproducing nifty50** (Q4). Run the automated loop on the same nifty50 H=25 cell and verify it reaches the conclusions documented by hand in `docs/gbdt/_147_nifty50_h25_manual_fs_hp_loop.md` (HP ceiling ~0.164, depth 6 optimal, monotone-contraindicated, prevalence-drift ceiling). `_147` is the answer key.
5. **Bundle = `diagnose.json` from `/gbdt-diagnose`** (Q5). The per-iteration bundle the agent reads is the output of the now-built `/gbdt-diagnose` skill (PR #51), run on that iteration's model against a once-built, cached in-sample matrix (fast after iter 0). **Supersedes the hand-written request-JSON schema in § 4.** Include the artifact dir path for ad-hoc deeper queries.
6. **Loop control files co-located under the artifact dir** (Q6): `results/gbdt/experiments/<cell>/loop/iter_<N>_{request,decision}.json` + the resume checkpoint. The agent operates on the absolute worktree path.

**Net architecture (final):** runner trains iter N → runs `/gbdt-diagnose` → writes `loop/iter_N_request.json` (= diagnose.json) + checkpoint → **exits** → harness notifies the agent → agent reads it (and may ask the user in chat) → writes `loop/iter_N_decision.json` → relaunch `--resume` → iter N+1. Heartbeat logging provides liveness; a large training timeout is the only backstop.

## § 1. The capability gap

Today: `walk_forward_train(..., fs_hp_callback=None)` calls `default_fs_hp_callback` when no callback is passed. `run_experiment()` never passes one, so every gbdt experiment to date has used the default (algorithmic prune + L2/cap nudge heuristic). The `/gbdt-experiment` SKILL.md aspirationally describes "agent-driven" mode; it isn't implemented.

What "agent-driven" was originally meant to be (per the skill doc): on every iteration the agent reads a "diagnostic bundle" and makes feature-pruning + HP-tuning decisions. The crucial unstated detail: **the agent is the user's Claude Code session**, not a separate Anthropic API call. The runner blocks; the user looks at the diagnostics and tells the runner what to do next; the runner applies the decision; repeat.

Why now: the H=25 cross-market memo (#138, post-fix-up #44) shows the fallback callback HURTS val_brier on NSE panels (every prune attempt degraded the loss). A human-driven loop could try different prune orders, HP combinations, ANY of the things a real data scientist would try when faced with degrading val_brier. The fallback is one fixed algorithm; the human-driven loop is open-ended.

## § 2. Architecture — file-based protocol

The runner and the user-as-sub-agent talk through **the filesystem**.

> **Superseded by § 0 (Q1): exit-and-resume, not block-and-poll.** The runner does not stay alive polling. The corrected mechanic is below.

For each iteration N, the runner:
1. Trains, then runs `/gbdt-diagnose` and writes `results/gbdt/experiments/<cell>/loop/iter_<N>_request.json` (= `diagnose.json`) + a resume checkpoint.
2. **Exits cleanly** (no polling). The harness's completion notification reaches the agent.
3. On the next launch, `python -m gbdt.experiment --resume <run_id>` loads the checkpoint + the agent's decision file, validates + applies it, and runs iter N+1.

The agent (the user's session):
1. Receives the completion notification.
2. Reads the diagnostic bundle (`diagnose.json`).
3. Reasons about it as a data scientist would (and asks the user in chat if a judgment call is needed — § 0 Q2).
4. Writes `loop/iter_<N>_decision.json`, then relaunches the runner with `--resume`.

**Why not inline Anthropic API**: the user wants their session's reasoning capabilities (full Claude Code context, can ask clarifying questions back to themselves, can pull additional code/data/charts on demand, can take their time, can switch contexts and come back). An inline `client.messages.create(...)` is a black-box single-shot call. The user's session is open-ended.

**Why not a separate sub-agent**: the prompt-engineering surface for "be a data scientist" inside a sub-agent is brittle — the sub-agent has no context window history with the user, can't ask clarifying questions, can't escalate decisions. The user IS the right place for this judgment.

**File-based protocol over REST/socket**: the user's tools already read/write files. Files are debuggable post-hoc. Files persist across session interrupts.

## § 3. How the user knows a decision is needed

Three plausible mechanisms; the plan picks one as default + documents the alternatives.

**(A) User runs the experiment in a Bash background task; checks on it periodically.**
- The Bash command is `uv run python -m gbdt.experiment <spec> --callback file_protocol`.
- It runs in `run_in_background=true` mode; harness tracks it; user gets a completion notification when the WHOLE experiment finishes.
- Between iterations, the user proactively reads `ls runs/<run_id>/iter_*_request.json` to see if a request is pending. Polling cadence: every few minutes during an active run.

**(B) Sidecar "decision-needed" notification.**
- Same as (A) but the runner also `touch`es a sentinel file when it starts waiting.
- A second Bash background process polls for the sentinel + exits when found.
- When the sidecar Bash exits, harness notifies the user → user reacts.

**(C) Iteration-as-separate-Bash-invocation.**
- The runner is refactored to support `--single-iter <N>` + checkpoint resume.
- The user runs one Bash per iteration; between iterations, they write the decision file then launch the next Bash.
- Most explicit; highest user friction.

**Plan picks (A)** as default — simplest implementation, user-driven cadence matches the actual workflow (user is engaged with the project, will check on the run naturally). (B) is the V1.2 follow-up if (A) feels awkward in practice. (C) is rejected (too much friction).

## § 6. The agent's role: what "data scientist tuning a model" means here

This is what I (the Claude Code session acting as the sub-agent) commit to doing per iteration:

1. **Read the diagnostic bundle in full.** Don't skim. The signal is in the details (per-ticker hit rates, feature importance distribution, calibration).
2. **Form a hypothesis** about what's working and what isn't:
   - If val_brier improved vs prior iter: what did the last decision change? Was the model just lucky, or is there a story?
   - If val_brier degraded: which families were dropped? Try reintroducing them or pruning differently.
   - If calibration z is bad: is the model overconfident on a specific cohort (see per-ticker)? Different remedies than uniform miscalibration.
   - If per-day P@k shape changed: did the model start picking different tickers?
3. **Pick decisions deliberately, not by template.** Don't just "always prune the lowest-importance feature". Reason about WHY that feature might be noise vs signal vs interaction-only.
4. **Track my own reasoning across iterations.** The prior-iterations field shows what I tried + what happened. Don't repeat failed experiments. If pruning X didn't help at iter 2, don't prune X again at iter 5.
5. **Know when to stop.** If 3+ iterations show no val_brier improvement and I've exhausted my hypotheses, emit `should_stop=true` with rationale. Don't burn iterations on diminishing returns.
6. **Ask questions when needed.** Use `questions_for_user` to surface a decision that needs human judgment (e.g., "we're at iter 5, val_brier is flat at 0.164, agent confidence is low — should we abandon this spec and try a different threshold?"). The runner halts on a question, surfaces it to the user, waits for response.
7. **Audit trail.** Every decision's `rationale` field is meant to read like a data scientist's lab notebook entry. Future readers (including future-me on the next experiment) should be able to follow the reasoning.

What I will NOT do:
- Touch the pinned HPs (`has_time`, `calibration_method`).
- Propose feature changes outside the spec's universe (no inventing new features mid-run).
- Make decisions I can't defend in the `rationale` field. If I'm guessing, I say so.

## § 7. Wiring into `run_experiment` (concrete code change)

`src/gbdt/__main__.py::run_experiment` gets a new spec-driven callback selection:

```python
# spec block (new):
backend:
  fs_hp_loop:
    max_iterations: 8
    callback_mode: agent_file_protocol   # NEW. Options: "default" | "agent_file_protocol"
    agent_options:
      request_timeout_seconds: 1800       # 30 min poll budget per iteration
      poll_interval_seconds: 10
      decision_path: runs/<run_id>/iter_{iter}_decision.json
      request_path:  runs/<run_id>/iter_{iter}_request.json
```

`run_experiment` resolves the callback based on `callback_mode`:

```python
def _resolve_callback(spec, run_id):
    mode = spec.backend.fs_hp_loop.callback_mode
    if mode == "default":
        return None  # walk_forward_train falls back to default_fs_hp_callback
    elif mode == "agent_file_protocol":
        opts = spec.backend.fs_hp_loop.agent_options
        return _make_file_protocol_callback(run_id=run_id, opts=opts)
    else:
        raise ValueError(f"unknown callback_mode: {mode}")

def _make_file_protocol_callback(run_id, opts):
    def cb(iter_n, diagnostic_bundle, spec, prior_iters):
        request_path = opts.request_path.format(iter=iter_n)
        decision_path = opts.decision_path.format(iter=iter_n)
        # 1. Serialize + write the request bundle
        Path(request_path).parent.mkdir(parents=True, exist_ok=True)
        Path(request_path).write_text(json.dumps(_build_bundle(...), indent=2))
        log(f"[loop] iter={iter_n} request written: {request_path}")
        # 2. Poll for decision
        log(f"[loop] iter={iter_n} waiting for decision: {decision_path}")
        elapsed = 0
        while elapsed < opts.request_timeout_seconds:
            if Path(decision_path).exists():
                log(f"[loop] iter={iter_n} decision received after {elapsed}s")
                decision = json.loads(Path(decision_path).read_text())
                _validate_decision(decision, spec)  # bounds, pinned, parseable
                return _decision_to_callback_return(decision)
            time.sleep(opts.poll_interval_seconds)
            elapsed += opts.poll_interval_seconds
        # 3. Timeout: log + fall back to default callback for this iter
        log(f"[loop] iter={iter_n} timeout after {elapsed}s — fallback to default callback")
        return default_fs_hp_callback(iter_n, diagnostic_bundle, spec, prior_iters)
    return cb
```

The runner emits a log line at every state transition (`request written`, `waiting for decision`, `decision received`, `timeout`) so the user can grep the run log to see exactly what happened.

Also new spec keys go into the spec-snapshot per PR #35; the runner's preflight log (per PR #39) includes `callback_mode` so post-hoc readers know what flavor of FS+HP loop drove the run.

## § 8. Stop conditions

Existing (preserved):
- val_brier plateau (improvement < `plateau_threshold` for N iterations)
- val_brier degradation (worsens by > `degradation_gate` from best)
- Budget exhaust (`max_iterations`)

New:
- Agent emits `should_stop: true` with rationale. Runner respects it.
- Agent emits `questions_for_user: [...]` non-empty. Runner halts, writes question to a separate sentinel file, waits indefinitely for either a follow-up decision or a CLI signal from the user.
- Request timeout (no decision in `request_timeout_seconds`): runner falls back to default callback for THAT iteration + logs the timeout. If 2+ consecutive timeouts → runner aborts the run with a "agent unresponsive" status (user can resume by writing the missing decision files + relaunching).

## § 9. Failure modes + recovery

| Failure | Detection | Recovery |
|---|---|---|
| Decision file is malformed JSON | `json.loads` raises | Runner logs the error, deletes the malformed file, re-polls — user notices the missing-decision condition + rewrites |
| Decision violates pinned HPs / search-space bounds | `_validate_decision` raises | Runner logs the specific violation, deletes the file, re-polls — user rewrites |
| `prune_features` references unknown feature names | Validation catches | Same — runner logs + deletes + re-polls |
| User session disconnects mid-iteration | Decision never arrives, timeout fires | Runner falls back to default callback for that iter — log captures the timeout |
| Runner process crashes mid-iter | Request file exists; runner is gone | User detects via "no Python process holding the request" — fixes the crash + relaunches `--resume <run_id>` (V1.2 feature; V1.1 may require manual rerun) |
| Disk fills, request write fails | `Path.write_text` raises | Runner aborts with a clear error — user investigates |
| Multiple runs share `runs/` accidentally | `run_id` collision | Runner refuses to start if `runs/<run_id>/` exists with files in it (unless `--overwrite`) |

**Phase 1**: parametrized test asserting `callback_mode=default` → callback is None (existing behavior preserved); `callback_mode=agent_file_protocol` → callback is the file-protocol implementation.

## § 12. Risks + mitigations

- **R1 — User session attention budget.** Each iteration requires the user to read the bundle + make a decision (15-30 min of attention per decision × 8 iter = 2-4 hours of focused attention per run). Mitigation: this is by design. The point is producing a high-quality model; if it takes the user 4 hours of focused work, that's the cost of doing it right. Future V1.2 might add a "delegate to a sub-agent for the easy iterations" mode, but V1.1 stays explicit.
- **R2 — File-protocol race conditions.** If the user writes the decision file before the runner finishes setting up the poll, the runner might miss it. Mitigation: the runner writes the request FIRST, then enters poll loop. The user always reads after request is visible. Polling timeout-and-retry handles transient FS issues.
- **R3 — User decides badly mid-run.** Possible. Mitigation: the existing val_brier-degradation gate kicks in if the user's decisions worsen the model materially. The run output preserves every decision + outcome for post-mortem.
- **R4 — Runner crashes mid-iteration.** No checkpoint/resume in V1.1. User has to restart from scratch. Mitigation: Phase 6 + future V1.2 work — add checkpoint after each successful iteration so a crashed run can resume from the last good iter.
- **R5 — Diagnostic bundle is too large for the user's context.** The full feature importance map (279 features) + per-ticker hit rate (50+ tickers) + prior iterations history could be tens of KB. Mitigation: the runner writes the FULL bundle to disk; the user reads only what's needed (via Read tool's `limit`/`offset`). They don't have to load the whole file into their context window.
- **R6 — Schema drift between runner and agent.** If the bundle schema changes, old runs' files become unreadable. Mitigation: add `schema_version: "v1"` field to both request + decision files. Increment on breaking changes.
- **R7 — User abandons mid-run.** Runner times out, falls back to default for remaining iters, completes the run. Cost: lost compute but no broken state.
