## Multi-target shared-tree head

Per v1.0 `V1_PLAN.md` open question #5, originally deferred to v2; promoted here as a v1.1 candidate if independent per-cell classifiers prove unreliable for correlated targets.

The hypothesis: targets like `up / +10% / 20d` and `up / +20% / 20d` are highly correlated events. Training them as independent classifiers wastes signal and may produce inconsistent calibration (e.g. the +20% classifier outputs a probability higher than the +10% classifier for the same row, which is logically impossible). A shared-tree head where the same trunk emits multiple target-specific predictions enforces consistency by construction.

Concrete shape:
- A new spec block `target.multi`: list of `(direction, threshold_pct, horizon_days)` tuples, all sharing one base model.
- CatBoost supports this via `MultiClass` / multi-target objectives; the calibration story gets harder (per-target Spiegelhalter Z applied to per-target predictions).
- Per-target calibration + a monotonicity check (smaller threshold should have higher probability for same row).

Gating: ship 2+ v1 experiments on correlated cells (e.g. `up/+10%/20d` and `up/+20%/20d`); measure whether the per-cell artifacts produce inconsistent probabilities on common rows. If yes, this gets promoted; if no (cells are calibrated and consistent), this stays parked.

## Lagged-target features with strict masking

Risky but high-information: features that incorporate *past* values of the target column itself (e.g. "fraction of past 60 days where the +10%/20d target fired"). Adds explicit regime memory that the model otherwise has to learn from features.

Why risky: target leakage is the #1 silent failure mode for these. A lag-1 of the target at row `t` looks like it uses data from `t-1`, but the target at `t-1` is computed from `(t, t+horizon]` close prices — which includes `t`, the row being predicted. The masking needs to lag by `horizon_days + 1` at minimum.

Concrete shape:
- New feature family `F18_target_lag_*` with strict horizon-aware masking.
- Mandatory: extend the Stage 1 leakage harness to specifically catch target-leak patterns (planted future-target signals at safe lag distances should still be detected if the masking is off).
- Each lagged-target feature is paired with a doctest demonstrating that its computation at row `t` uses only target values computed from price data with index `< t - horizon_days`.

Gating: the v1 leakage harness has to be proven robust on the simpler feature set first. F16 (signed-days-outside-band) already covers most of the "recent-event memory" intuition without the leakage trap, so this is gated on F16 proving insufficient.

## Per-experiment library override

Support LightGBM and XGBoost as alternative backends behind the same experiment-loop contract.

Concrete shape:
- `backend.library` in the spec accepts `"catboost" | "lightgbm" | "xgboost"`.
- `src/gbdt/model.py` grows a thin dispatch: each library has its own wrapper exposing the same `fit / predict_proba / save / load / feature_importance` interface.
- The HP reference doc (`CATBOOST_HP_REFERENCE.md`) gets siblings: `LIGHTGBM_HP_REFERENCE.md`, `XGBOOST_HP_REFERENCE.md`. The agent reads the right one based on `backend.library`.
- The walk-forward boundary discipline (`has_time=True` for CatBoost) needs the LightGBM / XGBoost equivalent (manual ordering enforcement; both libraries lack ordered-boosting machinery, so this is partly a "weaker correctness guarantee" tradeoff).

Gating: a concrete reason to switch (e.g. CatBoost wall-clock is the binding constraint for a real sweep, or a cell that CatBoost can't fit well). Otherwise CatBoost is fine.

## Multi-spec sweep runner

A single command that takes a list of spec files and runs them sequentially or in parallel.

Concrete shape:
- `python -m gbdt.sweep <spec_glob_or_list>` — discovers specs, runs each via `experiment.py`, emits a sweep-level summary report at `results/gbdt/sweeps/<sweep_name>/sweep.md` with per-experiment headline metrics in a single table.
- Parallelism via the same 4-worker pattern as `[[feedback-experiment-agent-loop]]`'s bulk-operations guidance.
- Optional: dependency declaration between specs (e.g. "use the best HP set from spec A as `hp_starting` for spec B").

Gating: at least 5–10 v1 experiments shipped one at a time first. The sweep runner is a convenience layer; running it before the single-experiment surface is battle-tested risks burning compute on a broken loop.

## Bayesian HP search alternative

Replace the agent-driven FS+HP loop with a Bayesian optimization library (Optuna) behind the same diagnostic-bundle contract.

Concrete shape:
- `backend.fs_hp_loop.driver: "agent" | "optuna"` in the spec. Default stays `"agent"`.
- When `"optuna"`, the loop iterates by Optuna trial: each trial reads the same diagnostic bundle the agent would have read, but the prune list comes from an importance-threshold pass and the HP changes come from Optuna's TPE sampler.
- Per-trial artifacts logged identically (same `iterations.jsonl` schema) so artifact-level tooling doesn't care which driver produced the loop.

Gating: if the agent loop proves inconsistent across runs in practice (e.g. same spec + same seed + different agent invocations produce materially different end states), this becomes the consistency-restoring fallback. Until that's measured, the agent loop has the design rationale on its side (cross-effects between features and HPs).

## Per-experiment baseline / null model comparison

Currently `metrics.json::headline_eval::brier_baseline_baserate` compares against the trivial "always predict the empirical positive rate" baseline. A v1.1 entry: add stronger baselines for the headline table.

Candidates:
- **Logistic regression** on a small fixed feature subset (e.g. `stock_return_20`, `realized_vol_20`, `rel_strength_20`). Common-sense baseline that a tree model should beat.
- **Marginal calibration baseline** — empirical CDF on the val segment applied to a single high-importance feature.
- **Per-stock base rate** (the panel's base rate is universe-pooled; per-stock can be quite different for some tickers).

Each adds one column to the report's per-experiment headline table. Cheap to compute; high informational value when interpreting a marginal Brier improvement.

Gating: ship a few v1 experiments first to see whether the trivial baseline is actually the bottleneck (or whether the v1 model is already comfortably beating it).
